ธนาคารออมสิน · ระบบงานสลากธนโชค

รีวิวระบบและแผนงาน

ฉบับรวม — ปิดการขายแล้วและกำลังย้ายแพลตฟอร์ม: ขอบเขตที่เหลือ ความเสี่ยง แผนงาน 5 เฟส และสิ่งที่ต้องให้เจ้าของระบบตัดสินใจ

โหมดจ่ายคืน (Run-off) ย้ายแพลตฟอร์ม → Linux + Docker + PostgreSQL ทบทวน 21 ฟังก์ชัน แผน 5 เฟส ฉบับร่างเพื่อหารือ

บทสรุปผู้บริหาร

สลากธนโชค ปิดการขายแล้ว เหลือเพียงรอผู้ถือสลากมาถอน — เป้าหมายระบบเปลี่ยนเป็น “จ่ายคืนให้ครบ แล้วปิดระบบ”
พร้อมกันนั้น มีมติย้ายแพลตฟอร์มแล้ว จาก Windows Server + MS SQL Server + Java/GlassFish ไปเป็น Linux (Ubuntu) + Docker + PostgreSQL ระบบใหม่อยู่ระหว่างเตรียมการ ยังไม่ขึ้นใช้งานจริง

มีสองงานใหญ่ทับซ้อนกัน — ระบบกำลังจะปิด (run-off) และกำลังย้ายแพลตฟอร์มไปพร้อมกัน ทั้งสองอย่างแย่งทรัพยากรและมีความเสี่ยงคนละแบบ ต้องวางลำดับให้ชัด

ความเสี่ยงใหญ่ที่สุดย้ายไปอยู่ที่การย้ายข้อมูล — MS SQL → PostgreSQL หมายถึงต้องเขียน Stored Procedure ทั้งชุดใหม่ และต้องพิสูจน์ว่ายอดเงินของลูกค้าตรงทุกบาท ข้อผิดพลาดตรงนี้กระทบเงินลูกค้าโดยตรง

ขอบเขตงานลดลงมาก — จาก 21 ฟังก์ชัน เหลือที่ต้องดูแลจริง 8 รายการ → ย้ายเฉพาะ 8 รายการนี้ก็พอ ไม่ต้องยกไปทั้งระบบ

ความปลอดภัยยังต้องแก้ทันทีบนระบบเดิม — การย้ายใช้เวลาหลายเดือน ระหว่างนั้นข้อมูลลูกค้ายังอยู่บนระบบที่รหัสผ่านใช้ซ้ำกันและเก็บไว้ในเอกสาร

ทำทันที (บนระบบเดิม)เปลี่ยนรหัสผ่านทุกบัญชีและลบรหัสผ่านออกจากเอกสาร — ไม่ต้องรอการย้ายแพลตฟอร์ม
ประหยัดได้ย้ายเฉพาะ 8 ฟังก์ชันที่ยังใช้จริง ปิดกลุ่ม B ก่อนย้าย — ลดงานเขียน SP ใหม่และงานทดสอบลงมาก
ต้องตัดสินใจก่อน Phase 3ระบบกำลังจะปิดอยู่แล้ว — ย้ายแพลตฟอร์มคุ้มกับความเสี่ยงการย้ายข้อมูลเงินลูกค้าหรือไม่
ส่วนที่ 1

ระบบคืออะไร

ธนโชค คือระบบงานสลากออมสิน รองรับข้อมูลผู้ถือสลาก ทะเบียนสลาก รายการธุรกรรม การออกและจ่ายรางวัล งานบริหารสาขา และการส่งข้อมูลออกผ่าน SFTP

เป็นระบบที่เกี่ยวกับ เงินและสิทธิ์ของลูกค้าโดยตรง — ความถูกต้องของข้อมูลและร่องรอยการตรวจสอบจึงสำคัญกว่าความเร็ว และในโหมดจ่ายคืน ร่องรอยการตรวจสอบยิ่งสำคัญขึ้น เพราะเป็นหลักฐานว่าจ่ายคืนใครไปแล้วบ้าง

สถาปัตยกรรม — ปัจจุบันและปลายทาง

ระบบที่ใช้งานอยู่วันนี้

ชั้นรายละเอียด
เครื่องให้บริการหน้าจอWindows Server 2019 · Java 1.6 · GlassFish (Java EE 6)

เป็น 2-tier แบบเครื่องละตัว ไม่มี cluster/failover · ตรรกะธุรกิจจำนวนมากอยู่ใน Stored Procedure (spl_UPDATE_PDCUST, PDMAST, PDTRN, PDRPZ, PDXREF, PRIZEAMT ฯลฯ) — เป็นจุดที่ย้ายยากที่สุด

หลักฐานที่สอดคล้อง: งาน SFTP Feed เตรียมสคริปต์ติดตั้งไว้ ทั้งฉบับ Windows (.bat) และฉบับ Linux/Unix (.sh) — สอดคล้องกับการเตรียมย้ายแพลตฟอร์ม
หมายเหตุเรื่องเอกสาร: หน้า TANACHOK ใน Notion (แก้ล่าสุดต้นเดือน ส.ค. 2569) ยังบันทึกสถาปัตยกรรมเป็น Windows + MS SQL อยู่ — ควรอัปเดตให้ตรงกับมติย้ายแพลตฟอร์ม เพื่อไม่ให้ผู้อ่านคนถัดไปสับสนแบบเดียวกัน

คงไว้  8 ฟังก์ชันที่ระบบยังต้องทำได้

ฟังก์ชันทำไมต้องคงไว้
A1ค้นหาผู้ถือสลากจุดเริ่มต้นของทุกเคสเมื่อลูกค้าเดินเข้าสาขา
A2แสดงยอดคงเหลือและสิทธิ์ที่พึงได้รับต้องรู้ว่าจ่ายคืนเท่าไร (เงินต้น + สิทธิ์ค้างจ่าย)
A3บันทึกการถอน/จ่ายคืนธุรกรรมประเภทเดียวที่ยังเกิดขึ้นจริง
A4ตรวจเงินรางวัลค้างจ่ายผู้ถือยังมีสิทธิ์รับรางวัลงวดเก่าที่ยังไม่ได้ขึ้นเงิน
A5ประวัติธุรกรรมรายผู้ถือสลากหลักฐานการจ่ายคืน ใช้ตอบข้อโต้แย้งและการตรวจสอบ
A6รายงานยอดคงค้างทั้งระบบฝ่ายบัญชีต้องรู้ภาระผูกพันที่เหลือ และใช้ติดตามความคืบหน้า
A7งานปิด/ย้ายสาขาสาขาทยอยปิด ต้องย้ายข้อมูลผู้ถือไปสาขาปลายทาง
A8จัดการผู้ใช้และสิทธิ์เข้าถึงควบคุมว่าใครจ่ายเงินได้ ใครดูข้อมูลได้

ตัดออก  7 ฟังก์ชันที่ไม่มีความหมายแล้ว

ฟังก์ชันเหตุผลวิธีจัดการ
B1ขาย/ซื้อสลากใหม่ไม่เปิดขายแล้วปิดเมนู + ปิดสิทธิ์
B2ฝากสลากเพิ่ม / ต่ออายุไม่มีการเพิ่มยอดอีกปิดเมนู
B3จัดสรรและออกเลขสลากไม่มีสลากใหม่ให้ออกเลขปิดงาน + หยุด job
B4ประมวลผลออกรางวัลงวดใหม่ไม่มีงวดใหม่แล้วปิดงาน แต่เก็บผลงวดเก่าไว้เพื่อ A4
B5รายงานยอดขาย / เป้า / อันดับสาขาไม่มีการขายให้วัดปิดรายงาน
B6ตัวเลขการขายบนหน้าภาพรวมไม่มีความหมายแล้วเปลี่ยนเป็นตัวเลขการจ่ายคืน
B7งานพิมพ์/จัดส่งสลากไม่มีสลากใหม่ปิดงาน
“ตัดออก” = ปิดการใช้งานและปิดสิทธิ์เท่านั้น — ห้ามลบข้อมูลเดิม ข้อมูลย้อนหลังทั้งหมดยังต้องเก็บตามระยะเวลาที่กำหนด เพื่อการตรวจสอบและการจ่ายคืน

รอตัดสินใจ  6 ประเด็น

ประเด็นทางเลือกผลต่อขอบเขตงาน
C1โอนสลาก / กรณีทายาทคงไว้เฉพาะมรดก หรือใช้กระบวนการเอกสารแทนถ้าคงไว้ ต้องคงหน้าจอโอนและกฎการตรวจสอบ
C2การส่งข้อมูลออก (SFTP Feed)ปลายทางยังต้องการไหม · ลดความถี่ได้ไหมถ้าเลิกส่ง ตัดงาน batch + การเฝ้าระวังทิ้งได้ทั้งชุด
C3การคิดดอกเบี้ย/ผลตอบแทนเดินต่อจนวันถอน หรือหยุด ณ วันที่กำหนดกระทบสูตรคำนวณยอดจ่ายคืน (A2)
C4ติดตามผู้ถือที่ยังไม่มาถอนมีแคมเปญตามตัวไหมถ้ามี ต้องเพิ่มรายงานติดตาม (งานเล็ก)
C5เงินที่ไม่มีผู้มาถอนตามกำหนดจัดการตามระเบียบใดต้องมีขั้นตอนและรายงานรองรับ
C6กำหนดวันปิดระบบมีกำหนดชัด หรือรอจนผู้ถือหมดเป็นตัวกำหนดว่าจะลงทุนกับระบบแค่ไหน
ส่วนที่ 4

ประเมินความพร้อม 16 ด้าน (ของระบบเดิมที่ยังใช้งานอยู่)

ประเมิน ระบบเดิมที่ยังให้บริการอยู่วันนี้ คอลัมน์สุดท้ายคือความเร่งด่วน เมื่อคำนึงว่าระบบกำลังปิดตัวและกำลังจะย้ายแพลตฟอร์ม — บางด้านแก้ที่ต้นเหตุด้วยการย้าย จึงไม่ต้องลงทุนบนระบบเดิม แต่บางด้าน (รหัสผ่าน สำรองข้อมูล ร่องรอยตรวจสอบ) รอไม่ได้

ด้านระดับสาระสำคัญความเร่งด่วนในโหมดจ่ายคืน
1เซิร์ฟเวอร์ & OSพร้อมย้ายขึ้น Windows Server 2019 แล้วทั้งสองเครื่อง—
2ฐานข้อมูลพร้อมMS SQL Server 2019 ติดตั้งแล้ว + ทดสอบกู้คืนสำเร็จ—
3Runtime (Java)ยังไม่มีหมดการสนับสนุนตั้งแต่ปี 2556 ไม่มี security patchแก้ด้วยการย้ายแพลตฟอร์ม — ระหว่างรอใช้มาตรการชดเชย
4Application Serverยังไม่มีหมดการสนับสนุน ไม่มีผู้ผลิตดูแลแก้ด้วยการย้ายแพลตฟอร์ม — เช่นเดียวกับข้อ 3
5การจัดการรหัสผ่านยังไม่มีใช้รหัสผ่านเริ่มต้นชุดเดียวกันทุกเครื่อง + เก็บในเอกสารสูงสุด — ไม่เปลี่ยน
6สิทธิ์การเข้าถึงบางส่วนยังใช้บัญชีร่วมกัน ไม่มีบัญชีรายบุคคลสูง — ไม่เปลี่ยน
7การสำรองข้อมูลบางส่วนทดสอบครั้งเดียวตอนย้าย ยังไม่มีตารางสำรองประจำสูงขึ้น — ต้องเป็นจุดย้อนกลับก่อนย้ายข้อมูล
8DR / ความต่อเนื่องยังไม่มีไม่มีเครื่องสำรอง ไม่มี RTO/RPO ที่ตกลงไว้ลดลง — ธุรกรรมต่ำ ยอมให้ RTO ยาวขึ้นได้
9การเฝ้าระวังและแจ้งเตือนยังไม่มีระบบล่มจะรู้เมื่อผู้ใช้แจ้งลดลง — เหลือเท่าที่จำเป็น
10ร่องรอยการตรวจสอบบางส่วนยังไม่ชัดว่าเก็บอะไร นานเท่าใดสูงขึ้น — เป็นหลักฐานการจ่ายคืน
11การนำระบบขึ้นใช้งานบางส่วนมีคู่มือแต่ทำมือ ย้อนกลับยากลดลงมาก — แทบไม่มี deploy แล้ว
12การคุมเวอร์ชันฐานข้อมูลยังไม่มีStored Procedure แก้ที่เครื่อง ไม่มีเวอร์ชันสูงขึ้น — ต้องคุมเวอร์ชันตอนเขียนใหม่บน PostgreSQL
13งานส่งข้อมูลออก (Feed)พร้อมscript ติดตั้งอัตโนมัติ + ชุดทดสอบครบ · มีฉบับ Linux แล้วขึ้นกับ C2 — อาจตัดทิ้งทั้งชุด
14ตารางงานอัตโนมัติบางส่วนต้องสร้างงานตามเวลาเอง ไม่มีการเฝ้าระวังผลขึ้นกับ C2
15เอกสารระบบบางส่วนมีคู่มือเฉพาะงาน ยังไม่รวมศูนย์สูงขึ้น — ป้องกันความรู้ผูกกับตัวบุคคล
16งานย้ายระบบที่ค้างบางส่วนยังมีงานค้างบางรายการคงเดิม
สรุป: พร้อม 3 · บางส่วน 7 · ยังไม่มี 6 → ระบบเดิมยังไม่ควรถือว่าพร้อม Production เต็มรูปแบบ

เมื่อรวมกับมติย้ายแพลตฟอร์ม แบ่งการลงทุนได้เป็น 3 กลุ่ม — ทำทันทีบนระบบเดิม (รอไม่ได้): รหัสผ่าน · สิทธิ์เข้าถึง · สำรองข้อมูล · ร่องรอยตรวจสอบ  ·  แก้ที่ต้นเหตุด้วยการย้าย: รันไทม์ · ตัวให้บริการเว็บ  ·  ต้องทำใหม่บนแพลตฟอร์มใหม่: การคุมเวอร์ชันฐานข้อมูล · การเฝ้าระวัง · การนำระบบขึ้นใช้งาน

รหัสผ่านเริ่มต้นถูกใช้ซ้ำทุกเครื่องและเก็บไว้ในเอกสาร

บัญชีผู้ดูแลของทั้ง Web Server และ DB Server รวมถึงหน้าจอผู้ดูแลของตัวให้บริการเว็บ ใช้รหัสผ่านเริ่มต้นชุดเดียวกัน และถูกบันทึกไว้ในเอกสารที่เปิดอ่านได้

ผลกระทบ: ผู้ที่เข้าถึงเอกสารได้ = เข้าถึงฐานข้อมูลลูกค้าและรายการจ่ายเงินได้ทันที

ต้องทำ: เปลี่ยนรหัสผ่านทุกบัญชีทันที บนระบบเดิม ไม่ต้องรอการย้ายแพลตฟอร์ม · แยกบัญชีรายบุคคล · ลบรหัสผ่านออกจากเอกสาร · และอย่ายกวิธีตั้งรหัสแบบเดิมไปแพลตฟอร์มใหม่
R2 · สูงมาก — ความเสี่ยงสูงสุดของโครงการ

การย้ายข้อมูลจาก MS SQL ไป PostgreSQL

ตรรกะธุรกิจจำนวนมากอยู่ใน Stored Procedure ของ MS SQL ซึ่ง ย้ายไป PostgreSQL ตรง ๆ ไม่ได้ ต้องเขียนใหม่และพิสูจน์ว่าให้ผลเหมือนเดิม

ผลกระทบ: ระบบนี้เก็บ ยอดเงินและสิทธิ์ของลูกค้า หากคำนวณเพี้ยนแม้เล็กน้อย จะกลายเป็นจ่ายคืนผิดจำนวน ซึ่งแก้ย้อนหลังยากและกระทบความเชื่อมั่นโดยตรง

ต้องทำ: เขียน Stored Procedure ใหม่เฉพาะที่ยังใช้จริง (กลุ่ม A) · กระทบยอดทุกบัญชีทุกบาท ระหว่างระบบเก่ากับใหม่ · รันคู่ขนาน เทียบผลอย่างน้อย 1 รอบเต็มก่อน cutover · มีแผนย้อนกลับหากผลไม่ตรง
R3 · สูงมาก

ความถูกต้องของภาษาไทยและชนิดข้อมูลหลังย้ายฐานข้อมูล

ชื่อ-ที่อยู่ลูกค้าเป็นภาษาไทย การย้ายข้ามชนิดฐานข้อมูลมักเจอปัญหา encoding/collation และความต่างของชนิดข้อมูลตัวเลขทศนิยม

ผลกระทบ: ชื่อลูกค้าเพี้ยน ค้นหาไม่เจอ หรือยอดเงินปัดเศษต่างจากเดิม

ต้องทำ: กำหนด encoding เป็น UTF-8 ตั้งแต่ต้น · ตรวจตัวอย่างข้อมูลจริงที่มีสระ/วรรณยุกต์ · ใช้ชนิดข้อมูลตัวเลขที่ไม่ปัดเศษสำหรับจำนวนเงิน
R4 · สูงมาก

ทำสองงานใหญ่พร้อมกันบนทีมเดียว

ระบบกำลังปิดตัว (run-off) และย้ายแพลตฟอร์มไปพร้อมกัน ขณะที่สาขาก็ทยอยปิด

ผลกระทบ: ทรัพยากรถูกแบ่ง งานใดงานหนึ่งอาจค้างกลางทาง และช่วง cutover เป็นช่วงที่เสี่ยงที่สุดสำหรับลูกค้าที่มาถอน

ต้องทำ: เรียงลำดับให้ชัด — ความปลอดภัยก่อน · ย้ายแพลตฟอร์มทีหลัง · หลีกเลี่ยง cutover ช่วงที่มีผู้มาถอนหนาแน่น
R5–R8 · สูง

รันไทม์ระหว่างรอย้าย · สำรองข้อมูล · ร่องรอยตรวจสอบ · ความรู้ผูกกับบุคคล

R5 รันไทม์เดิมยังหมดการสนับสนุนตลอดช่วงที่ยังไม่ย้ายเสร็จ — ต้องจำกัดการเข้าถึงเครือข่าย อย่างเข้มงวดและบันทึกเป็นข้อยกเว้นที่อนุมัติแล้ว โดยกำหนดวันสิ้นสุดผูกกับแผน cutover

R6 การสำรองข้อมูลยังไม่เป็นระบบ และยิ่งสำคัญขึ้นเมื่อจะย้ายฐานข้อมูล เพราะต้องมีจุดย้อนกลับที่เชื่อถือได้ — ต้องซ้อมกู้คืนให้ผ่านก่อนเริ่มย้ายข้อมูล

R7 ร่องรอยการตรวจสอบต้องไม่ขาดตอนตรงรอยต่อ — ต้องยกประวัติธุรกรรมเดิมไปด้วย และทดสอบว่าค้นย้อนหลังได้จริงหลังย้าย

R8 ความรู้ผูกกับตัวบุคคล — ช่วงย้ายแพลตฟอร์มและปิดระบบมักมีการโยกย้ายคน เสี่ยงกว่าปกติ

R9–R12 · ปานกลาง

อีก 4 เรื่องที่ต้องไม่ลืม

ไม่มีเครื่องสำรอง (ผลกระทบต่ำลงในโหมดจ่ายคืน แต่ยังต้องตกลงเวลากู้คืน) · การเฝ้าระวังยังไม่มีและต้องเตรียมไว้บนแพลตฟอร์มใหม่ด้วย · งาน Feed ต้องย้ายไป Linux (สคริปต์ .sh เตรียมไว้แล้วแต่ยังไม่ทดสอบจริง) · เอกสาร Notion ยังบันทึกสถาปัตยกรรมเก่า ควรอัปเดตให้ตรงมติ

ส่วนที่ 7

แผนงาน 5 เฟส

หลักการเรียงลำดับ: ความปลอดภัยก่อน · ย้ายแพลตฟอร์มทีหลัง — เพราะการย้ายใช้เวลาหลายเดือน แต่ความเสี่ยงด้านรหัสผ่านรอไม่ได้
Phase 1
สัปดาห์ 1–2

ปิดความเสี่ยงเร่งด่วนบนระบบเดิม

  • เปลี่ยนรหัสผ่านทุกบัญชีบน Web/DB Server และหน้าจอผู้ดูแล
  • เลิกใช้บัญชีร่วม — ออกบัญชีรายบุคคลตามบทบาท
  • ลบรหัสผ่านออกจากเอกสารทุกฉบับ ย้ายไปตู้เก็บรหัสที่ควบคุมสิทธิ์
  • จำกัดการเข้าถึงเครือข่าย (มาตรการชดเชยของ R5 จนกว่าจะ cutover)
  • ปิดเมนูและปิดสิทธิ์ฟังก์ชันกลุ่ม B ทั้ง 7 รายการ — ทำก่อนย้าย เพื่อไม่ต้องยกงานที่เลิกใช้ไปแพลตฟอร์มใหม่
Phase 2
สัปดาห์ 3–6

ทำให้ดูแลได้จริงและเตรียมจุดย้อนกลับ

  • ตั้งตารางสำรองข้อมูล + ตรวจสอบไฟล์สำรองอัตโนมัติ
  • ซ้อมกู้คืนจริง 1 ครั้ง — ต้องผ่านก่อนเริ่มย้ายข้อมูลใน Phase 3
  • กำหนดนโยบายการเก็บร่องรอยการตรวจสอบ
  • ติดตั้งการเฝ้าระวังพื้นฐาน (บริการ ดิสก์ ฐานข้อมูล)
  • ตัดสินใจเรื่อง Feed — ถ้าเลิกส่ง ตัดออกจากขอบเขตการย้ายไปเลย
Phase 3
สัปดาห์ 7–16

เตรียมย้ายแพลตฟอร์ม งานหนักที่สุด

  • ยืนยันขอบเขตที่จะย้าย = เฉพาะ 8 ฟังก์ชันกลุ่ม A
  • เขียน Stored Procedure ที่ยังใช้จริงใหม่บน PostgreSQL
  • ย้ายโครงสร้างและข้อมูลจริง พร้อมกำหนด encoding ภาษาไทยและชนิดข้อมูลจำนวนเงิน
  • กระทบยอด (reconciliation) ทุกบัญชีทุกบาท เทียบระบบเก่า–ใหม่
  • ยกประวัติธุรกรรมเดิมไปด้วย และทดสอบว่าค้นย้อนหลังได้จริง
  • ย้ายงาน Feed ไปสคริปต์ฉบับ Linux + ทดสอบตามชุด TC เดิม (ถ้ายังต้องส่ง)
  • นำโค้ดและสคริปต์ย้ายข้อมูลเข้าระบบควบคุมเวอร์ชัน + จัดทำคู่มือปฏิบัติการ
  • ยื่นเอกสารขอใช้ CI/CD กับทีม QA ตั้งแต่ต้นเฟส (4 ฉบับ ตามแบบ LK)
  • จัดทำ Base Image นำส่งธนาคาร — Jenkins ธนาคารไม่ต่ออินเทอร์เน็ต
  • ตั้ง repo ใน GitLab ธนาคาร + branch main/dev + กำหนดผู้อนุมัติ MR ฝั่งธนาคาร
  • ทำ vite build ใน pipeline แล้วเสิร์ฟผ่าน nginx — เลิกใช้ Vite dev server
  • ฝัง Tag version ลง image + ทำหน้าจอแสดง version ตามกติกาธนาคาร
Phase 4
หลัง Phase 3

รันคู่ขนานและ Cutover

  • รันคู่ขนาน (parallel run) อย่างน้อย 1 รอบเต็ม เทียบผลระบบเก่า–ใหม่
  • ให้ผู้ใช้จริงทดสอบการจ่ายคืนบนระบบใหม่ (UAT)
  • กำหนดเกณฑ์ผ่าน/ไม่ผ่าน และ แผนย้อนกลับหากยอดไม่ตรง
  • ปรับ Deploy Checklist ของ LK เป็นฉบับธนโชค + เพิ่มข้อตรวจยอดเงินลูกค้าหลัง deploy
  • เลือกช่วง cutover ที่มีผู้มาถอนน้อย + แจ้งสาขาล่วงหน้า
  • cutover แล้วเฝ้าระวังใกล้ชิดช่วงแรก · ปลดระวางเครื่อง Windows เดิมเมื่อระบบใหม่นิ่ง
Phase 5
รอกำหนดวัน

แผนปิดระบบ

  • กำหนดวันสิ้นสุดการรับคำขอถอน และแจ้งผู้ถือสลากล่วงหน้า
  • กำหนดวิธีจัดการยอดที่ไม่มีผู้มาถอนตามระเบียบ
  • วางแผนเก็บข้อมูลถาวรให้ค้นย้อนหลังได้หลังปิดระบบ
  • กำหนดวิธีให้บริการหากมีผู้มาติดต่อหลังปิดระบบ
  • ปลดระวางระบบและเพิกถอนสิทธิ์เข้าถึงทั้งหมด
ข้อสังเกตเชิงกลยุทธ์: Phase 3–4 เป็นงานหนักและมีความเสี่ยงเรื่องเงินลูกค้า ขณะที่ Phase 5 คือการปิดระบบอยู่ดี — ถ้าวันปิดระบบอยู่ใกล้พอ อาจคุ้มกว่าที่จะคงระบบเดิม พร้อมมาตรการชดเชยจนถึงวันปิด แทนการย้ายแพลตฟอร์ม ควรตัดสินใจข้อนี้ก่อนเริ่ม Phase 3

Deploy Checklist — ยืมของ LK มาปรับใช้ได้เลย

LK2 มี Deploy Checklist ครบ 3 ชุด (ก่อน deploy / หลัง deploy / rollback) นำมาปรับเป็นฉบับธนโชคได้ทันที จุดที่ต้องแก้:

  • สำรองฐานข้อมูล — LK ใช้ MySQL (mysqldump) ธนโชคใช้ PostgreSQL → เปลี่ยนเป็น pg_dump
  • วิธี rollback — เปลี่ยน IMAGE_TAG ใน .env แล้ว restart · ห้ามใช้ --force-recreate (LK ระบุไว้ชัด เพราะข้อมูลใน volume จะหาย)
  • ตัดสินใจ rollback ภายใน 15 นาที — ใช้ได้เหมือนกัน
ข้อที่ต้องเพิ่มเฉพาะธนโชค: ตรวจยอดคงเหลือของลูกค้าหลัง deploy ทุกครั้ง — LK ไม่มีข้อนี้เพราะไม่ได้ถือเงินลูกค้า แต่ธนโชคถือ ห้ามข้าม

บทเรียนจาก LK ที่ควรเผื่อเวลา

  • กระบวนการขอใช้ CI/CD เป็นงานเอกสารหลายฉบับ + ขอเปิด firewall + ประสานหลายทีม (QA, Firewall, Security, Operation) — ใช้เวลาระดับสัปดาห์ถึงเดือน ไม่ใช่วัน
  • Security Team เป็นคอขวดที่อยู่นอกการควบคุมของทีม — เผื่อเวลารอผลการ scan
  • ระบบอยู่ในโหมดจ่ายคืนและกำลังจะปิด ไม่ต้องสร้าง pipeline เกินจำเป็น ทำตามมาตรฐาน 4 pipeline ของธนาคารก็เพียงพอ

หน้าจอที่เสนอ

ตัวอย่างหน้าจอ 3 หน้าปรับให้ตรงขอบเขตที่เหลือ — ใช้เป็นสเปกตั้งต้นของระบบใหม่ได้ด้วย

หน้าจอสาระสำคัญ
1 · ภาพรวมการจ่ายคืนยอดคงค้างรอจ่ายคืน · จ่ายคืนวันนี้ · เงินรางวัลค้างจ่าย · ความคืบหน้าการปิด + อัตราการมาถอนรายเดือน
2 · ค้นหาผู้ถือสลาก และจ่ายคืนหน้าจอสำคัญที่สุด — ค้นหา ตรวจยอดที่ต้องจ่าย แล้วบันทึกการจ่ายคืนจบในหน้าเดียว
3 · รายงานความคืบหน้าการจ่ายคืนยอดคงค้างแยกตามสาขา + ประมาณการว่าอีกกี่ปีจะปิดระบบได้
ส่วนที่ 10

สิ่งที่ต้องให้เจ้าของระบบตัดสินใจ

ประเด็นทำไมสำคัญบล็อกงานอะไร
1ย้ายแพลตฟอร์มคุ้มกับความเสี่ยงหรือไม่ เมื่อระบบกำลังจะปิดถ้าวันปิดใกล้พอ การคงระบบเดิมพร้อมมาตรการชดเชยอาจเสี่ยงน้อยกว่าPhase 3–4 ทั้งหมด
2ปลายทางของ Feed ยังต้องการข้อมูลหรือไม่ตัดได้ทั้งชุด และไม่ต้องยกไปแพลตฟอร์มใหม่Phase 2–3
3ยืนยันว่าย้ายเฉพาะ 8 ฟังก์ชันกลุ่ม A ได้หรือไม่ลดงานเขียน SP ใหม่และงานทดสอบลงมากขอบเขต Phase 3
4เกณฑ์การกระทบยอดที่ยอมรับได้คืออะไรต้องตรงทุกบาท หรือมีเกณฑ์ผ่อนผันPhase 4 (เกณฑ์ cutover)
5มีกำหนดวันปิดระบบหรือยังกำหนดว่าจะลงทุนกับระบบแค่ไหนPhase 5 · และข้อ 1
6เหลือผู้ถือกี่ราย ยอดคงค้างเท่าไรประเมินว่าต้องรันระบบอีกนานเท่าใดการวางแผนทั้งหมด
7ยอดจ่ายคืนคิดอย่างไร (ยังคิดผลตอบแทนต่อไหม)กระทบสูตรคำนวณและการเขียน SP ใหม่Phase 3 · หน้าจอ 2
8เงินที่ไม่มีผู้มาถอนจัดการตามระเบียบใดต้องมีขั้นตอนและรายงานรองรับPhase 5
9ยอมให้ระบบหยุดได้นานเท่าใด (RTO)ออกแบบขั้นตอนกู้คืน + ช่วง cutoverPhase 2 · Phase 4
10ยอมให้ข้อมูลหายได้ถึงจุดใด (RPO)กำหนดความถี่การสำรองข้อมูลPhase 2
11ต้องเก็บข้อมูลย้อนหลังกี่ปีหลังปิดระบบกำหนดวิธีเก็บข้อมูลถาวรPhase 5
12กรณีทายาท/มรดก รองรับในระบบหรือใช้เอกสารกระทบว่าจะคงหน้าจอโอนไว้หรือไม่ขอบเขต A
13ต้องมีแคมเปญติดตามผู้ถือหรือไม่ถ้ามี ต้องเพิ่มรายงานติดตามขอบเขต A
14ใครดูแลระบบและอนุมัติการเปลี่ยนแปลงตั้งขั้นตอน change managementPhase 3
15มีข้อกำหนดจากผู้กำกับ/ผู้ตรวจสอบเพิ่มหรือไม่ปรับแผนให้สอดคล้องทั้งหมด
ส่วนที่ 11

ข้อเสนอแนะสรุป

ข้อเสนอแนะ
1เริ่ม Phase 1 ทันทีบนระบบเดิม — อย่ารอการย้าย เพราะการย้ายใช้เวลาหลายเดือน ระหว่างนั้นข้อมูลลูกค้ายังอยู่บนระบบที่รหัสผ่านใช้ซ้ำกันและเก็บไว้ในเอกสาร
2ตัดสินใจข้อ 1 ในตารางก่อนเริ่ม Phase 3 — ระบบกำลังจะปิดอยู่แล้ว ถ้าวันปิดใกล้พอ การคงระบบเดิมพร้อมมาตรการชดเชยอาจเสี่ยงน้อยกว่าและถูกกว่าการย้ายฐานข้อมูลที่เก็บยอดเงินลูกค้า
3ถ้าย้าย — ย้ายเฉพาะ 8 ฟังก์ชันกลุ่ม A และปิดกลุ่ม B ก่อนย้าย จะลดงานเขียน SP ใหม่และงานทดสอบลงอย่างมาก
4การกระทบยอดคือหัวใจ ไม่ใช่การย้ายให้เสร็จ — ต้องรันคู่ขนานเทียบผลอย่างน้อย 1 รอบเต็ม และมีแผนย้อนกลับที่ใช้ได้จริง ก่อนตัดสินใจ cutover
5ซ้อมกู้คืนให้ผ่านก่อนแตะข้อมูล — เป็นจุดย้อนกลับเดียวที่มีถ้าการย้ายผิดพลาด
6อัปเดตเอกสารใน Notion ให้ตรงมติย้ายแพลตฟอร์ม — ตอนนี้ยังบันทึกเป็น Windows + MS SQL ทำให้ผู้อ่านเข้าใจผิดได้ (เกิดขึ้นแล้วในการจัดทำเอกสารชุดนี้)
7ต่อยอดของดีที่มีอยู่ — งาน SFTP Feed ทำมาตรฐานได้ดีและเตรียมสคริปต์ฉบับ Linux ไว้แล้ว ใช้เป็นต้นแบบของงานย้ายส่วนอื่น

ฉบับร่างเพื่อใช้หารือกับเจ้าของระบบ · ตัวเลขระยะเวลาและข้อสรุปทุกข้อรอการยืนยันจากผู้เกี่ยวข้อง · สถาปัตยกรรมปลายทางอ้างอิงมติย้ายแพลตฟอร์มที่ได้รับการยืนยันจากทีมงาน (เอกสารใน Notion ยังไม่ได้อัปเดต) · เอกสารนี้ไม่มีรหัสผ่าน ชื่อเครื่อง หรือ IP ของระบบโดยเจตนา
