ธนาคารออมสิน · ระบบงานสลากธนโชค

รีวิวระบบและแผนงาน

ฉบับรวม — สถานะระบบ ขอบเขตที่เหลือหลังปิดการขาย ความเสี่ยง แผนงาน และสิ่งที่ต้องให้เจ้าของระบบตัดสินใจ

โหมดจ่ายคืน (Run-off) ประเมิน 16 ด้าน ทบทวน 21 ฟังก์ชัน แผน 5 เฟส ฉบับร่างเพื่อหารือ

บทสรุปผู้บริหาร

สลากธนโชค ปิดการขายแล้ว เหลือเพียงรอผู้ถือสลากมาถอน ระบบจึงอยู่ใน โหมดจ่ายคืน (Run-off) — เป้าหมายเปลี่ยนจาก “ให้บริการต่อเนื่อง” เป็น “จ่ายคืนให้ครบ แล้วปิดระบบ”

แผนเดิมเขียนผิดระบบ — ฉบับก่อนหน้าอ้างอิง stack นักพัฒนาในเครื่อง (Docker) ระบบจริงคือ Windows Server 2019 สองเครื่อง + Java 1.6 + GlassFish + MS SQL Server 2019

ยังไม่ควรถือว่าพร้อม Production เต็มรูปแบบ — ประเมิน 16 ด้าน ได้ พร้อม 3 · บางส่วน 7 · ยังไม่มี 6 โครงสร้างพื้นฐานย้ายเครื่องใหม่เรียบร้อยแล้ว แต่ยังขาดด้านความปลอดภัย ความต่อเนื่อง และการเฝ้าระวัง

ขอบเขตงานลดลงมาก — จาก 21 ฟังก์ชัน เหลือที่ต้องดูแลจริง 8 รายการ ตัดออกได้ 7 และรอเจ้าของระบบตัดสินใจ 6

ความเสี่ยงด้านความปลอดภัยไม่ได้ลดลงเลย — ปิดการขายไม่ได้ทำให้ข้อมูลลูกค้าและเงินที่ยังอยู่ในระบบปลอดภัยขึ้น และผู้ตรวจสอบยังตรวจระบบที่ยังมีข้อมูลอยู่

ทำทันทีเปลี่ยนรหัสผ่านทุกบัญชีและลบรหัสผ่านออกจากเอกสาร — เริ่มได้เลยโดยไม่ต้องรอคำตอบข้ออื่น
ประหยัดได้ยกเลิก Phase 4 (ยกระดับรันไทม์/พัฒนาใหม่) ทั้งเฟส — ไม่คุ้มที่จะรื้อระบบที่กำลังจะปิด
ต้องได้คำตอบปลายทาง Feed ยังต้องการข้อมูลไหม · มีกำหนดวันปิดระบบหรือยัง · เหลือผู้ถือกี่ราย
ส่วนที่ 1

ระบบคืออะไร

ธนโชค คือระบบงานสลากออมสิน รองรับข้อมูลผู้ถือสลาก ทะเบียนสลาก รายการธุรกรรม การออกและจ่ายรางวัล งานบริหารสาขา (ปิดสาขาและย้ายข้อมูลไปสาขาปลายทาง) และการส่งข้อมูลออกผ่าน SFTP ไปยังระบบปลายทาง

เป็นระบบที่เกี่ยวกับ เงินและสิทธิ์ของลูกค้าโดยตรง — ความถูกต้องของข้อมูลและร่องรอยการตรวจสอบจึงสำคัญกว่าความเร็ว และในโหมดจ่ายคืน ความสำคัญของร่องรอยการตรวจสอบยิ่งสูงขึ้น เพราะเป็นหลักฐานว่าจ่ายคืนใครไปแล้วบ้าง

คงไว้  8 ฟังก์ชันที่ระบบยังต้องทำได้

ฟังก์ชันทำไมต้องคงไว้
A1ค้นหาผู้ถือสลากจุดเริ่มต้นของทุกเคสเมื่อลูกค้าเดินเข้าสาขา
A2แสดงยอดคงเหลือและสิทธิ์ที่พึงได้รับต้องรู้ว่าจ่ายคืนเท่าไร (เงินต้น + สิทธิ์ค้างจ่าย)
A3บันทึกการถอน/จ่ายคืนธุรกรรมประเภทเดียวที่ยังเกิดขึ้นจริง
A4ตรวจเงินรางวัลค้างจ่ายผู้ถือยังมีสิทธิ์รับรางวัลงวดเก่าที่ยังไม่ได้ขึ้นเงิน
A5ประวัติธุรกรรมรายผู้ถือสลากหลักฐานการจ่ายคืน ใช้ตอบข้อโต้แย้งและการตรวจสอบ
A6รายงานยอดคงค้างทั้งระบบฝ่ายบัญชีต้องรู้ภาระผูกพันที่เหลือ และใช้ติดตามความคืบหน้า
A7งานปิด/ย้ายสาขาสาขาทยอยปิด ต้องย้ายข้อมูลผู้ถือไปสาขาปลายทาง
A8จัดการผู้ใช้และสิทธิ์เข้าถึงควบคุมว่าใครจ่ายเงินได้ ใครดูข้อมูลได้

ตัดออก  7 ฟังก์ชันที่ไม่มีความหมายแล้ว

ฟังก์ชันเหตุผลวิธีจัดการ
B1ขาย/ซื้อสลากใหม่ไม่เปิดขายแล้วปิดเมนู + ปิดสิทธิ์
B2ฝากสลากเพิ่ม / ต่ออายุไม่มีการเพิ่มยอดอีกปิดเมนู
B3จัดสรรและออกเลขสลากไม่มีสลากใหม่ให้ออกเลขปิดงาน + หยุด job
B4ประมวลผลออกรางวัลงวดใหม่ไม่มีงวดใหม่แล้วปิดงาน แต่เก็บผลงวดเก่าไว้เพื่อ A4
B5รายงานยอดขาย / เป้า / อันดับสาขาไม่มีการขายให้วัดปิดรายงาน
B6ตัวเลขการขายบนหน้าภาพรวมไม่มีความหมายแล้วเปลี่ยนเป็นตัวเลขการจ่ายคืน
B7งานพิมพ์/จัดส่งสลากไม่มีสลากใหม่ปิดงาน
“ตัดออก” = ปิดการใช้งานและปิดสิทธิ์เท่านั้น — ห้ามลบข้อมูลเดิม ข้อมูลย้อนหลังทั้งหมดยังต้องเก็บตามระยะเวลาที่กำหนด เพื่อการตรวจสอบและการจ่ายคืน

รอตัดสินใจ  6 ประเด็น

ประเด็นทางเลือกผลต่อขอบเขตงาน
C1โอนสลาก / กรณีทายาทคงไว้เฉพาะมรดก หรือใช้กระบวนการเอกสารแทนถ้าคงไว้ ต้องคงหน้าจอโอนและกฎการตรวจสอบ
C2การส่งข้อมูลออก (SFTP Feed)ปลายทางยังต้องการไหม · ลดความถี่ได้ไหมถ้าเลิกส่ง ตัดงาน batch + การเฝ้าระวังทิ้งได้ทั้งชุด
C3การคิดดอกเบี้ย/ผลตอบแทนเดินต่อจนวันถอน หรือหยุด ณ วันที่กำหนดกระทบสูตรคำนวณยอดจ่ายคืน (A2)
C4ติดตามผู้ถือที่ยังไม่มาถอนมีแคมเปญตามตัวไหมถ้ามี ต้องเพิ่มรายงานติดตาม (งานเล็ก)
C5เงินที่ไม่มีผู้มาถอนตามกำหนดจัดการตามระเบียบใดต้องมีขั้นตอนและรายงานรองรับ
C6กำหนดวันปิดระบบมีกำหนดชัด หรือรอจนผู้ถือหมดเป็นตัวกำหนดว่าจะลงทุนกับระบบแค่ไหน
ส่วนที่ 3

ประเมินความพร้อม 16 ด้าน

คอลัมน์สุดท้ายคือความเร่งด่วน หลังปิดการขาย — บางด้านที่เคยสำคัญมากลดระดับลง ขณะที่ร่องรอยการตรวจสอบและเอกสารกลับสำคัญขึ้น

ด้านระดับสาระสำคัญความเร่งด่วนในโหมดจ่ายคืน
1เซิร์ฟเวอร์ & OSพร้อมย้ายขึ้น Windows Server 2019 แล้วทั้งสองเครื่อง—
2ฐานข้อมูลพร้อมMS SQL Server 2019 ติดตั้งแล้ว + ทดสอบกู้คืนสำเร็จ—
3Runtime (Java)ยังไม่มีหมดการสนับสนุนตั้งแต่ปี 2556 ไม่มี security patchลดลง — ใช้มาตรการชดเชยแทนการยกระดับ
4Application Serverยังไม่มีหมดการสนับสนุน ไม่มีผู้ผลิตดูแลลดลง — เช่นเดียวกับข้อ 3
5การจัดการรหัสผ่านยังไม่มีใช้รหัสผ่านเริ่มต้นชุดเดียวกันทุกเครื่อง + เก็บในเอกสารสูงสุด — ไม่เปลี่ยน
6สิทธิ์การเข้าถึงบางส่วนยังใช้บัญชีร่วมกัน ไม่มีบัญชีรายบุคคลสูง — ไม่เปลี่ยน
7การสำรองข้อมูลบางส่วนทดสอบครั้งเดียวตอนย้าย ยังไม่มีตารางสำรองประจำสูง — ไม่เปลี่ยน
8DR / ความต่อเนื่องยังไม่มีไม่มีเครื่องสำรอง ไม่มี RTO/RPO ที่ตกลงไว้ลดลง — ธุรกรรมต่ำ ยอมให้ RTO ยาวขึ้นได้
9การเฝ้าระวังและแจ้งเตือนยังไม่มีระบบล่มจะรู้เมื่อผู้ใช้แจ้งลดลง — เหลือเท่าที่จำเป็น
10ร่องรอยการตรวจสอบบางส่วนยังไม่ชัดว่าเก็บอะไร นานเท่าใดสูงขึ้น — เป็นหลักฐานการจ่ายคืน
11การนำระบบขึ้นใช้งานบางส่วนมีคู่มือแต่ทำมือ ย้อนกลับยากลดลงมาก — แทบไม่มี deploy แล้ว
12การคุมเวอร์ชันฐานข้อมูลยังไม่มีStored Procedure แก้ที่เครื่อง ไม่มีเวอร์ชันลดลง — เหลือเพียงคุมสิทธิ์การแก้ไข
13งานส่งข้อมูลออก (Feed)พร้อมscript ติดตั้งอัตโนมัติ + ชุดทดสอบครบขึ้นกับ C2 — อาจตัดทิ้งทั้งชุด
14ตารางงานอัตโนมัติบางส่วนต้องสร้างงานตามเวลาเอง ไม่มีการเฝ้าระวังผลขึ้นกับ C2
15เอกสารระบบบางส่วนมีคู่มือเฉพาะงาน ยังไม่รวมศูนย์สูงขึ้น — ป้องกันความรู้ผูกกับตัวบุคคล
16งานย้ายระบบที่ค้างบางส่วนยังมีงานค้างบางรายการคงเดิม
สรุป: พร้อม 3 · บางส่วน 7 · ยังไม่มี 6 → ยังไม่ควรถือว่าพร้อม Production เต็มรูปแบบ แต่ในโหมดจ่ายคืน สิ่งที่ต้องเร่งเหลือเพียงกลุ่มความปลอดภัยและร่องรอยการตรวจสอบ ส่วนงานสถาปัตยกรรม CI/CD และ HA ลดความสำคัญลงอย่างมีนัยสำคัญ
ส่วนที่ 4

ความเสี่ยง

R1 · สูงมาก

รหัสผ่านเริ่มต้นถูกใช้ซ้ำทุกเครื่องและเก็บไว้ในเอกสาร

บัญชีผู้ดูแลของทั้ง Web Server และ DB Server รวมถึงหน้าจอผู้ดูแลของตัวให้บริการเว็บ ใช้รหัสผ่านเริ่มต้นชุดเดียวกัน และถูกบันทึกไว้ในเอกสารที่เปิดอ่านได้

ผลกระทบ: ผู้ที่เข้าถึงเอกสารได้ = เข้าถึงฐานข้อมูลลูกค้าและรายการจ่ายเงินได้ทันที เป็นข้อบกพร่องร้ายแรงในสายตาผู้ตรวจสอบ

ต้องทำ: เปลี่ยนรหัสผ่านทุกบัญชีทันที · แยกบัญชีรายบุคคล · เลิกใช้บัญชีร่วม · ย้ายความลับไปเก็บในตู้เก็บรหัสผ่านที่ควบคุมสิทธิ์ · ลบรหัสผ่านออกจากเอกสารทั้งหมด
R2 · สูงมาก

รันไทม์และตัวให้บริการเว็บหมดการสนับสนุน

Java 1.6 สิ้นสุดการสนับสนุนตั้งแต่ปี 2556 · GlassFish รุ่น Java EE 6 ไม่มีผู้ผลิตดูแลแล้ว

ผลกระทบ: ช่องโหว่ที่พบใหม่จะไม่มีแพตช์แก้ และไม่ผ่านการสแกนตามมาตรฐานธนาคาร

ต้องทำ (ปรับตามโหมดจ่ายคืน): ไม่ยกระดับรันไทม์ เพราะไม่คุ้มกับอายุที่เหลือของระบบ ให้ใช้ มาตรการชดเชย แทน — จำกัดการเข้าถึงเครือข่ายอย่างเข้มงวด ให้เข้าถึงได้เฉพาะเครื่องและผู้ใช้ที่จำเป็น และบันทึกเป็นข้อยกเว้นที่ได้รับอนุมัติพร้อมกำหนดวันสิ้นสุด
R3 · สูงมาก

ไม่มีเครื่องสำรองและยังไม่ได้ตกลงเวลากู้คืน

มีเครื่องละหนึ่งตัว หากเสียหายระบบจะหยุดจนกว่าจะกู้คืนเสร็จ

ผลกระทบ: ในโหมดจ่ายคืนผลกระทบต่ำลง (ลูกค้ามาถอนไม่ใช่งานเร่งด่วนรายนาที) แต่ยังต้องมีเวลากู้คืนที่ตกลงกันไว้ ไม่ใช่ปล่อยไม่กำหนด

ต้องทำ: ตกลง RTO/RPO ที่ยอมรับได้ในบริบทนี้ แล้วออกแบบการสำรองให้ได้ตามนั้น (อาจไม่ต้องมีเครื่องสำรองพร้อมใช้ แต่ต้องมีขั้นตอนกู้คืนที่ซ้อมแล้ว)
R4–R6 · สูง

การสำรองข้อมูล · ร่องรอยตรวจสอบ · ความรู้ผูกกับตัวบุคคล

R4 การสำรองข้อมูลยังไม่เป็นระบบ — ทดสอบกู้คืนครั้งเดียวตอนย้ายเครื่อง ยังไม่มีตารางสำรองประจำ และไม่มีการตรวจว่าไฟล์สำรองใช้ได้จริง

R5 ร่องรอยการตรวจสอบยังไม่ชัดเจน — ในโหมดจ่ายคืนนี่คือหลักฐานว่าจ่ายเงินให้ใครไปแล้ว ต้องกำหนดว่าเก็บอะไร ระบุตัวผู้ทำรายการได้ และเก็บนานเท่าใด

R6 ความรู้ผูกกับตัวบุคคล — เอกสารกระจายตามงาน ไม่มีคู่มือปฏิบัติการรวมศูนย์ ช่วงปิดระบบมักมีการโยกย้ายคน ทำให้เสี่ยงกว่าปกติ

R7–R10 · ปานกลาง

อีก 4 เรื่องที่ลดระดับลงในโหมดจ่ายคืน

การเฝ้าระวังยังไม่มี (ควรมีพื้นฐาน: บริการ ดิสก์ ฐานข้อมูล) · งาน Feed ต้องสร้างงานตามเวลาเองและไม่รู้ผลรัน (ขึ้นกับ C2) · ตรรกะอยู่ใน Stored Procedure โดยไม่มีการคุมเวอร์ชัน (เหลือเพียงคุมสิทธิ์การแก้ไข) · งานย้ายระบบยังค้างบางรายการ (ควรปิดให้จบเพื่อไม่ให้เป็นภาระค้าง)

ส่วนที่ 5

จากปัจจุบัน สู่เป้าหมาย

ด้านปัจจุบันเป้าหมาย
ขอบเขตระบบ21 ฟังก์ชัน รวมงานขายที่ไม่ใช้แล้วเหลือ 8 ฟังก์ชันที่จำเป็นต่อการจ่ายคืน
ความปลอดภัยบัญชีรหัสผ่านชุดเดียวกัน เก็บในเอกสารบัญชีรายบุคคล + เก็บรหัสในระบบที่ควบคุมสิทธิ์
รันไทม์ที่หมดการสนับสนุนไม่มีมาตรการรองรับจำกัดการเข้าถึงเป็นมาตรการชดเชย + บันทึกเป็นข้อยกเว้นที่อนุมัติแล้ว
ความต่อเนื่องเครื่องเดียว ไม่มีข้อตกลงเวลากู้คืนมีขั้นตอนกู้คืนที่ซ้อมแล้ว ตาม RTO/RPO ที่ตกลง
การสำรองข้อมูลทดสอบครั้งเดียวตอนย้ายเครื่องสำรองตามตาราง + ซ้อมกู้คืนประจำ มีบันทึกผล
ร่องรอยการตรวจสอบไม่ชัดเจนเก็บครบ ระบุตัวผู้ทำรายการได้ ตรวจย้อนหลังได้
การส่งข้อมูลออกตั้งเวลาทำมือ ไม่รู้ผลรันตั้งเวลาอัตโนมัติ + แจ้งเตือน หรือยกเลิกทั้งชุดตาม C2
เอกสารกระจายตามงานคู่มือปฏิบัติการรวมศูนย์
ปลายทางของระบบไม่มีแผนปิดมีวันปิดระบบ วิธีจัดการยอดค้าง และแผนเก็บข้อมูลถาวร
ส่วนที่ 6

แผนงาน 5 เฟส

ระยะเวลาเป็นประมาณการเพื่อใช้หารือ ต้องยืนยันกับเจ้าของระบบและหน่วยงานที่เกี่ยวข้อง

Phase 1
สัปดาห์ 1–2

ปิดความเสี่ยงเร่งด่วน คงไว้เต็มรูปแบบ

  • เปลี่ยนรหัสผ่านทุกบัญชีบน Web/DB Server และหน้าจอผู้ดูแล
  • เลิกใช้บัญชีร่วม — ออกบัญชีรายบุคคลตามบทบาท
  • ลบรหัสผ่านออกจากเอกสารทุกฉบับ ย้ายไปตู้เก็บรหัสที่ควบคุมสิทธิ์
  • จำกัดการเข้าถึงเครือข่ายให้เหลือเท่าที่จำเป็น (มาตรการชดเชยของ R2)
  • ทบทวนว่าใครมีสิทธิ์เข้าถึงระบบอยู่บ้างในปัจจุบัน
  • ปิดเมนูและปิดสิทธิ์ฟังก์ชันกลุ่ม B ทั้ง 7 รายการ (ห้ามลบข้อมูล)
Phase 2
สัปดาห์ 3–6

ทำให้ดูแลได้จริง ลดขนาด

  • ตั้งตารางสำรองข้อมูล + ตรวจสอบไฟล์สำรองอัตโนมัติ
  • ซ้อมกู้คืนจริง 1 ครั้ง จับเวลาเทียบกับ RTO ที่ตกลง
  • กำหนดนโยบายการเก็บร่องรอยการตรวจสอบ (สำคัญขึ้นในโหมดนี้)
  • ติดตั้งการเฝ้าระวังพื้นฐาน (บริการ ดิสก์ ฐานข้อมูล) — ลดขอบเขตจากแผนเดิม
  • ปิดงานย้ายระบบที่ยังค้าง
  • งาน Feed: ตั้งงานตามเวลา + เฝ้าระวัง หรือยกเลิกทั้งชุด — รอคำตอบ C2
Phase 3
สัปดาห์ 7–12

คุมการเปลี่ยนแปลง เหลือเท่าที่จำเป็น

  • คุมสิทธิ์การแก้ไขระบบและฐานข้อมูล
  • นำ Stored Procedure ที่ยังใช้งานเข้าระบบควบคุมเวอร์ชัน
  • จัดทำคู่มือปฏิบัติการรวมศูนย์ + กำหนดผู้อนุมัติการเปลี่ยนแปลง
Phase 4
ยกเลิก

ยกระดับรันไทม์ / พัฒนาใหม่ ยกเลิกทั้งเฟส

ไม่คุ้มที่จะรื้อระบบที่กำลังจะปิด — เป็นการประหยัดที่ใหญ่ที่สุดจากเงื่อนไขใหม่นี้ ความเสี่ยงจากรันไทม์เก่าให้จัดการด้วยมาตรการชดเชยใน Phase 1 แทน

Phase 5
รอกำหนดวัน

แผนปิดระบบ เพิ่มใหม่

  • กำหนดวันสิ้นสุดการรับคำขอถอน และแจ้งผู้ถือสลากล่วงหน้า
  • กำหนดวิธีจัดการยอดที่ไม่มีผู้มาถอนตามระเบียบ
  • วางแผนเก็บข้อมูลถาวร (archive) ให้ค้นย้อนหลังได้หลังปิดระบบ
  • กำหนดวิธีให้บริการหากมีผู้มาติดต่อหลังปิดระบบ
  • ปลดระวางเครื่องและเพิกถอนสิทธิ์เข้าถึงทั้งหมด
ส่วนที่ 7

หน้าจอที่เสนอ

ตัวอย่างหน้าจอ 3 หน้าปรับให้ตรงขอบเขตที่เหลือ — ดูฉบับเต็มได้ในหน้าตัวอย่างหน้าจอแยกต่างหาก

หน้าจอสาระสำคัญ
1 · ภาพรวมการจ่ายคืนยอดคงค้างรอจ่ายคืน · จ่ายคืนวันนี้ · เงินรางวัลค้างจ่าย · ความคืบหน้าการปิด + อัตราการมาถอนรายเดือน
2 · ค้นหาผู้ถือสลาก และจ่ายคืนหน้าจอสำคัญที่สุด — ค้นหา ตรวจยอดที่ต้องจ่าย (แยกเงินต้น/รางวัลค้างจ่าย/ผลตอบแทน) แล้วบันทึกการจ่ายคืนจบในหน้าเดียว
3 · รายงานความคืบหน้าการจ่ายคืนยอดคงค้างแยกตามสาขา + ประมาณการว่าอีกกี่ปีจะปิดระบบได้
หลักการออกแบบที่ใช้: เมนูที่ปิดแล้ว (ขายสลาก ฝากเพิ่ม ตรวจรางวัลงวดใหม่) ยังแสดงแบบจางขีดฆ่า เพื่อให้ผู้ใช้เข้าใจว่า ปิดโดยตั้งใจ ไม่ใช่ระบบเสีย และรายการธุรกรรมเก่าคงไว้พร้อมทำเครื่องหมาย “รายการเดิม” — ข้อมูลไม่ถูกลบ แต่ผู้ใช้รู้ว่าทำรายการแบบนั้นใหม่ไม่ได้แล้ว
ส่วนที่ 8

สิ่งที่ต้องให้เจ้าของระบบตัดสินใจ

ประเด็นทำไมสำคัญบล็อกงานอะไร
1ปลายทางของ Feed ยังต้องการข้อมูลหรือไม่ตัดได้ทั้งชุดถ้าไม่ต้องการPhase 2 (ประหยัดมากที่สุด)
2มีกำหนดวันปิดระบบหรือยังกำหนดว่าจะลงทุนกับระบบแค่ไหนPhase 5 ทั้งเฟส
3เหลือผู้ถือกี่ราย ยอดคงค้างเท่าไรประเมินว่าต้องรันระบบอีกนานเท่าใดการวางแผนทั้งหมด
4ยอดจ่ายคืนคิดอย่างไร (ยังคิดผลตอบแทนต่อไหม)กระทบสูตรคำนวณและหน้าจอA2 · หน้าจอ 2
5เงินที่ไม่มีผู้มาถอนจัดการตามระเบียบใดต้องมีขั้นตอนและรายงานรองรับPhase 5
6ยอมให้ระบบหยุดได้นานเท่าใด (RTO)ออกแบบขั้นตอนกู้คืนPhase 2
7ยอมให้ข้อมูลหายได้ถึงจุดใด (RPO)กำหนดความถี่การสำรองข้อมูลPhase 2
8ต้องเก็บข้อมูลย้อนหลังกี่ปีหลังปิดระบบกำหนดวิธีเก็บข้อมูลถาวรPhase 5
9กรณีทายาท/มรดก รองรับในระบบหรือใช้เอกสารกระทบว่าจะคงหน้าจอโอนไว้หรือไม่ขอบเขต A
10ต้องมีแคมเปญติดตามผู้ถือหรือไม่ถ้ามี ต้องเพิ่มรายงานติดตามขอบเขต A
11ใครดูแลระบบและอนุมัติการเปลี่ยนแปลงตั้งขั้นตอน change managementPhase 3
12มีข้อกำหนดจากผู้กำกับ/ผู้ตรวจสอบเพิ่มหรือไม่ปรับแผนให้สอดคล้องทั้งหมด
ส่วนที่ 9

ข้อเสนอแนะสรุป

ข้อเสนอแนะ
1เริ่ม Phase 1 ทันที — ไม่ต้องรอคำตอบข้ออื่น เป็นงานที่ใช้เวลาน้อย ต้นทุนต่ำ แต่ลดความเสี่ยงได้มากที่สุด และเป็นสิ่งที่ผู้ตรวจสอบมองหาเป็นอันดับแรก
2ลดขอบเขตให้เหลือ 8 ฟังก์ชัน และปิดกลุ่ม B ทันที — ลดพื้นที่เสี่ยง ลดความสับสนของผู้ใช้ และลดงานดูแล โดยห้ามลบข้อมูล
3ยกเลิก Phase 4 — การประหยัดที่ใหญ่ที่สุด และเปลี่ยนวิธีจัดการความเสี่ยงรันไทม์จาก “ยกระดับ” เป็น “จำกัดการเข้าถึง + บันทึกเป็นข้อยกเว้นที่อนุมัติแล้ว”
4เร่งถามเรื่อง Feed — จุดเดียวที่ตัดแล้วประหยัดงานได้มากที่สุดทันที
5เริ่มคุยเรื่องวันปิดระบบตั้งแต่ตอนนี้ — เป็นตัวกำหนดทุกอย่างที่เหลือ และเป็นงานที่ต้องใช้เวลาประสานหลายฝ่าย
6ต่อยอดของดีที่มีอยู่ — งาน SFTP Feed ทำมาตรฐานได้ดี (สคริปต์ทำซ้ำได้ + ชุดทดสอบครบ) ใช้เป็นต้นแบบกับงานอื่น เช่น การสำรองข้อมูลและการกู้คืน

ฉบับร่างเพื่อใช้หารือกับเจ้าของระบบ · ตัวเลขระยะเวลาและข้อสรุปทุกข้อรอการยืนยันจากผู้เกี่ยวข้อง · เอกสารนี้ไม่มีรหัสผ่าน ชื่อเครื่อง หรือ IP ของระบบโดยเจตนา
