# TANACHOK (สลากธนโชค) — รีวิวฟังก์ชันสำหรับโหมดปิดการขาย (Run-off)

> **เงื่อนไขใหม่:** สลากธนโชค **ไม่เปิดขายแล้ว** เหลือเพียง **รอให้ลูกค้ามาถอน**
> เอกสารฉบับนี้ทบทวนว่าฟังก์ชันใดต้องคงไว้ ตัดออก หรือรอการตัดสินใจ
> และผลกระทบต่อแผนทำให้ระบบพร้อม Production ที่เสนอไว้ก่อนหน้า

---

## 0. สิ่งที่เปลี่ยนไปจากแผนเดิม (สำคัญที่สุด)

แผนก่อนหน้าตั้งอยู่บนสมมติฐานว่า **ธนโชคเป็นระบบที่ยังเปิดให้บริการเต็มรูปแบบ**
เมื่อระบบเข้าสู่โหมดปิดการขาย เหตุผลเชิงลงทุนเปลี่ยนทั้งหมด:

| ประเด็น | แผนเดิม (ระบบเปิดให้บริการ) | แผนใหม่ (โหมดปิดการขาย) |
|---|---|---|
| เป้าหมายระบบ | ให้บริการต่อเนื่องระยะยาว | **จ่ายคืนผู้ถือสลากให้ครบ แล้วปิดระบบ** |
| Phase 4 ยกระดับ/พัฒนาใหม่ | เสนอให้ประเมิน | **ตัดออก** — ไม่ควรลงทุนรื้อระบบที่กำลังจะเลิกใช้ |
| ความพร้อมใช้งาน (HA) | ต้องการสูง | **ลดระดับได้** — ปริมาณธุรกรรมต่ำมาก |
| เวลากู้คืน (RTO) | ต้องสั้น | **ยืดหยุ่นได้** — ลูกค้ามาถอนไม่ใช่งานเร่งด่วนรายนาที |
| ความปลอดภัย | ต้องแก้ | **ยังต้องแก้เหมือนเดิม** — ข้อมูลลูกค้าและเงินยังอยู่ |
| ร่องรอยตรวจสอบ | ต้องมี | **สำคัญขึ้นกว่าเดิม** — เป็นหลักฐานการจ่ายคืน |
| สิ่งที่ต้องเพิ่มใหม่ | — | **แผนปิดระบบ (Sunset Plan)** และการจัดการยอดที่ไม่มีผู้มาถอน |

**ข้อสรุปเชิงงบประมาณ:** งานที่ควรทำลดลงมาก — เหลือเฉพาะ **ความปลอดภัย + การจ่ายคืนที่ถูกต้อง
+ ร่องรอยตรวจสอบ + แผนปิดระบบ** ส่วนงานยกระดับสถาปัตยกรรมและ CI/CD ควรพับเก็บ

## 1. กลุ่ม A — คงไว้ (จำเป็นต่อการจ่ายคืน)

| # | ฟังก์ชัน | ทำไมต้องคงไว้ |
|---|---|---|
| A1 | **ค้นหาผู้ถือสลาก** (เลขที่สลาก / เลขบัตร / ชื่อ) | จุดเริ่มต้นของทุกเคส เมื่อลูกค้าเดินเข้าสาขา |
| A2 | **แสดงยอดคงเหลือและสิทธิ์ที่พึงได้รับ** | ต้องรู้ว่าจ่ายคืนเท่าไร (เงินต้น + สิทธิ์ค้างจ่าย) |
| A3 | **บันทึกการถอน/จ่ายคืน** | ธุรกรรมประเภทเดียวที่ยังเกิดขึ้นจริง |
| A4 | **ตรวจเงินรางวัลค้างจ่าย** (งวดที่ออกไปแล้ว) | ผู้ถือยังมีสิทธิ์รับรางวัลงวดเก่าที่ยังไม่ได้ขึ้นเงิน |
| A5 | **ประวัติธุรกรรมรายผู้ถือสลาก** | หลักฐานการจ่ายคืน ใช้ตอบข้อโต้แย้งและการตรวจสอบ |
| A6 | **รายงานยอดคงค้างทั้งระบบ** | ฝ่ายบัญชีต้องรู้ภาระผูกพันที่เหลือ และใช้ติดตามความคืบหน้าการปิด |
| A7 | **งานปิด/ย้ายสาขา** | ยังจำเป็น — สาขาทยอยปิด ต้องย้ายข้อมูลผู้ถือไปสาขาปลายทาง |
| A8 | **จัดการผู้ใช้และสิทธิ์เข้าถึง** | ควบคุมว่าใครจ่ายเงินได้ ใครดูข้อมูลได้ |

> ทั้ง 8 รายการนี้คือ **ขอบเขตขั้นต่ำที่ระบบต้องทำได้** จนกว่าจะปิดระบบจริง

## 2. กลุ่ม B — ตัดออกได้ (ไม่มีการขายแล้ว)

| # | ฟังก์ชัน | เหตุผลที่ตัดได้ | วิธีจัดการ |
|---|---|---|---|
| B1 | **ขาย/ซื้อสลากใหม่** | ไม่เปิดขายแล้ว | ปิดเมนู + ปิดสิทธิ์ในระบบ |
| B2 | **ฝากสลากเพิ่ม / ต่ออายุ** | ไม่มีการเพิ่มยอดอีก | ปิดเมนู |
| B3 | **จัดสรรและออกเลขสลาก** (งาน running number) | ไม่มีสลากใหม่ให้ออกเลข | ปิดงาน + หยุด job ที่เกี่ยวข้อง |
| B4 | **ประมวลผลออกรางวัลงวดใหม่** | ไม่มีงวดใหม่แล้ว | ปิดงาน (แต่ **เก็บผลงวดเก่าไว้** เพื่อ A4) |
| B5 | **รายงานยอดขาย / เป้าการขาย / อันดับสาขา** | ไม่มีการขายให้วัด | ปิดรายงาน |
| B6 | **ตัวเลขการขายบนหน้าภาพรวม** | ไม่มีความหมายแล้ว | เปลี่ยนเป็นตัวเลขการจ่ายคืน (ดูข้อ 4) |
| B7 | **งานพิมพ์/จัดส่งสลาก** | ไม่มีสลากใหม่ | ปิดงาน |

> **คำเตือนสำคัญ:** "ตัดออก" ในที่นี้หมายถึง **ปิดการใช้งานและปิดสิทธิ์** — **ห้ามลบข้อมูลเดิม**
> ข้อมูลย้อนหลังทั้งหมดยังต้องเก็บไว้ตามระยะเวลาที่กำหนด เพื่อการตรวจสอบและการจ่ายคืน

## 3. กลุ่ม C — ต้องให้เจ้าของระบบตัดสินใจ

| # | ประเด็น | ทางเลือก | ผลต่อขอบเขตงาน |
|---|---|---|---|
| C1 | **โอนสลากระหว่างบุคคล / กรณีทายาท** | คงไว้เฉพาะกรณีมรดก · หรือปิดทั้งหมดแล้วใช้กระบวนการเอกสารแทน | ถ้าคงไว้ ต้องคงหน้าจอโอนและกฎการตรวจสอบ |
| C2 | **การส่งข้อมูลออก (SFTP Feed)** | ปลายทางยังต้องการข้อมูลอยู่ไหม · ถ้าต้องการ ลดความถี่จากรายวันเป็นรายเดือนได้ไหม | ถ้าเลิกส่ง ตัดงาน batch + การเฝ้าระวังทิ้งได้ทั้งชุด |
| C3 | **การคิดดอกเบี้ย/ผลตอบแทน** | ยังเดินต่อจนถึงวันถอน · หรือหยุดคิด ณ วันที่กำหนด | กระทบสูตรคำนวณยอดจ่ายคืน (A2) |
| C4 | **การติดต่อผู้ถือที่ยังไม่มาถอน** | มีแคมเปญตามตัวไหม · ต้องมีรายงานรายชื่อ/ที่อยู่ไหม | ถ้ามี ต้องเพิ่มรายงานติดตาม (งานเล็ก) |
| C5 | **เงินที่ไม่มีผู้มาถอนภายในกำหนด** | จัดการตามระเบียบอย่างไร (โอนเป็นรายได้ / ส่งหน่วยงานที่กำกับ) | ต้องมีขั้นตอนและรายงานรองรับ |
| C6 | **กำหนดวันปิดระบบ (Sunset date)** | มีกำหนดชัดเจนหรือรอจนผู้ถือหมด | เป็นตัวกำหนดว่าจะลงทุนกับระบบแค่ไหน |

## 4. ผลต่อหน้าจอที่เสนอไว้

### หน้าจอ 1 — ภาพรวมระบบ
เปลี่ยนตัวเลขจาก "การขาย" เป็น **"ความคืบหน้าการจ่ายคืน"**

| เดิม | ใหม่ |
|---|---|
| ยอดสลากคงเหลือ | **ยอดคงค้างรอจ่ายคืน** (จำนวนราย + จำนวนเงิน) |
| ธุรกรรมวันนี้ | **จ่ายคืนวันนี้** (จำนวนราย + จำนวนเงิน) |
| รอตรวจจ่ายรางวัล | **เงินรางวัลค้างจ่ายที่ยังไม่มีผู้รับ** |
| งาน Feed รอบล่าสุด | **ความคืบหน้าการปิด** (จ่ายคืนแล้วกี่ % ของยอดตั้งต้น) |

เพิ่ม: กราฟ/ตัวเลขแนวโน้มว่าเหลือผู้ถืออีกกี่ราย และอัตราการมาถอนต่อเดือน
ตัดออก: เมนูงานที่ใช้บ่อยที่เกี่ยวกับการขายและการตรวจรางวัลงวดใหม่

### หน้าจอ 2 — ค้นหาผู้ถือสลาก
**คงไว้เกือบทั้งหมด — เป็นหน้าจอที่สำคัญที่สุดในโหมดนี้**
- คงไว้: การค้นหา รายละเอียด ประวัติธุรกรรม
- เปลี่ยน: ปุ่มหลักเป็น **"บันทึกการจ่ายคืน"** แทนเมนูรายการทั่วไป
- เพิ่ม: ช่อง **ยอดที่ต้องจ่ายคืน ณ วันนี้** ให้เด่นชัด (เงินต้น + สิทธิ์ค้างจ่าย)
- ประวัติธุรกรรม: แสดงรายการเก่าได้ตามเดิม แต่รายการใหม่จะมีเฉพาะการจ่ายคืน

### หน้าจอ 3 — การส่งข้อมูลออก (Feed)
**ขึ้นกับข้อ C2** — ถ้าปลายทางเลิกต้องการข้อมูล ให้ **ตัดหน้าจอนี้ทิ้งทั้งหน้า**
พร้อมงาน batch และการเฝ้าระวังที่เกี่ยวข้อง (ประหยัดงานได้มากที่สุดในบรรดาข้อเสนอทั้งหมด)

### หน้าจอที่ควรเพิ่มใหม่
**รายงานความคืบหน้าการจ่ายคืน** — เหลือผู้ถือกี่ราย ยอดเท่าไร แยกตามสาขา/ช่วงเวลา
ใช้รายงานต่อผู้บริหารและใช้ตัดสินใจว่าจะปิดระบบเมื่อใด

## 5. ผลต่อแผนงานที่เสนอไว้

| เฟสเดิม | สถานะใหม่ | เหตุผล |
|---|---|---|
| **Phase 1 — ปิดความเสี่ยงเร่งด่วน** | **คงไว้ทั้งหมด · ยังเร่งด่วนเท่าเดิม** | ข้อมูลลูกค้าและเงินยังอยู่ในระบบ ความเสี่ยงไม่ได้ลดลงเพราะปิดการขาย |
| **Phase 2 — ทำให้ดูแลได้จริง** | **คงไว้ แต่ลดขนาด** | สำรองข้อมูล + ร่องรอยตรวจสอบยังจำเป็น · การเฝ้าระวังลดเหลือเท่าที่จำเป็น · ถ้าเลิก Feed ตัดส่วนนั้นทิ้ง |
| **Phase 3 — คุมการเปลี่ยนแปลง** | **ลดเหลือเท่าที่จำเป็น** | ระบบแทบไม่มีการแก้ไขแล้ว เหลือเพียงคุมว่าใครแก้อะไรได้ + เก็บเอกสารปฏิบัติการ |
| **Phase 4 — ยกระดับ/พัฒนาใหม่** | **ตัดออก** | ไม่คุ้มที่จะรื้อระบบที่กำลังจะปิด |
| **(ใหม่) Phase 5 — แผนปิดระบบ** | **เพิ่มเข้ามา** | กำหนดวันปิด · จัดการยอดที่ไม่มีผู้มาถอน · เก็บข้อมูลถาวร · ปลดระวางเครื่อง |

### Phase 5 (ใหม่) — แผนปิดระบบ
- [ ] กำหนดวันสิ้นสุดการรับคำขอถอน และแจ้งผู้ถือสลากล่วงหน้า
- [ ] กำหนดวิธีจัดการยอดที่ไม่มีผู้มาถอนตามระเบียบ
- [ ] วางแผนเก็บข้อมูลถาวร (archive) ให้ค้นย้อนหลังได้หลังปิดระบบ
- [ ] กำหนดว่าหลังปิดระบบ ถ้ามีผู้มาติดต่อภายหลังจะให้บริการอย่างไร
- [ ] ปลดระวางเครื่องและเพิกถอนสิทธิ์เข้าถึงทั้งหมด

## 6. คำถามที่ต้องได้คำตอบก่อนสรุปขอบเขต

| # | คำถาม | ทำไมสำคัญ |
|---|---|---|
| 1 | ตอนนี้เหลือผู้ถือสลากกี่ราย ยอดคงค้างเท่าไร | เป็นตัวกำหนดว่าคุ้มลงทุนแค่ไหน และต้องรันระบบอีกนานเท่าใด |
| 2 | มีกำหนดวันปิดระบบหรือยัง | ถ้ามีกำหนดชัด งานทั้งหมดจะวางแผนได้แม่นขึ้นมาก |
| 3 | อัตราการมาถอนต่อเดือนเป็นเท่าใด | ใช้ประมาณว่าอีกกี่ปีจึงจะหมด |
| 4 | ปลายทางของ Feed ยังต้องการข้อมูลอยู่หรือไม่ | ตัดได้ทั้งชุดถ้าไม่ต้องการ (ประหยัดงานมากที่สุด) |
| 5 | ยังคิดดอกเบี้ย/ผลตอบแทนอยู่หรือไม่ | กระทบสูตรคำนวณยอดจ่ายคืน |
| 6 | เงินที่ไม่มีผู้มาถอนจัดการตามระเบียบใด | ต้องมีขั้นตอนและรายงานรองรับ |
| 7 | กรณีทายาท/มรดก ยังต้องรองรับในระบบหรือใช้เอกสาร | กระทบว่าจะคงหน้าจอโอนไว้หรือไม่ |
| 8 | ต้องเก็บข้อมูลย้อนหลังกี่ปีหลังปิดระบบ | กำหนดวิธี archive |

## 7. ข้อเสนอแนะสรุป

1. **ลดขอบเขตให้เหลือ 8 ฟังก์ชันในกลุ่ม A** — นี่คือสิ่งที่ระบบต้องทำได้จริงในโหมดนี้
2. **ปิดการใช้งานกลุ่ม B ทันที** — ลดพื้นที่เสี่ยง ลดความสับสนของผู้ใช้ และลดงานดูแล
   โดย **ห้ามลบข้อมูล** เพียงปิดเมนูและปิดสิทธิ์
3. **ยกเลิก Phase 4 (ยกระดับ/พัฒนาใหม่)** — เป็นการประหยัดที่ใหญ่ที่สุดจากเงื่อนไขใหม่นี้
4. **ยังต้องทำ Phase 1 (ความปลอดภัย) เต็มรูปแบบ** — ปิดการขายไม่ได้ทำให้ข้อมูลลูกค้าปลอดภัยขึ้น
   และผู้ตรวจสอบยังตรวจระบบที่ยังมีข้อมูลอยู่
5. **เพิ่ม Phase 5 แผนปิดระบบ** — ควรเริ่มคุยตั้งแต่ตอนนี้ เพราะเป็นตัวกำหนดทุกอย่างที่เหลือ
6. **ถามข้อ C2 (Feed) ให้ได้คำตอบเร็วที่สุด** — เป็นจุดเดียวที่ตัดแล้วประหยัดงานได้มากที่สุดทันที
