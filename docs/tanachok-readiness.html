รีวิวความพร้อมขึ้น Production

ประเมินว่าระบบธนโชคพร้อมใช้งานบน Production จริงหรือยัง ขาดอะไร และต้องทำอะไรก่อน — เพื่อใช้หารือกับเจ้าของระบบ

ฉบับร่างเพื่อหารือ ประเมิน 16 ด้าน อ้างอิงเอกสารโครงการจริง ตัวเลขระยะเวลารอการยืนยัน

ระบบคืออะไร

ธนโชค — ระบบงานสลากออมสิน

รองรับข้อมูลผู้ถือสลาก ทะเบียนสลาก รายการธุรกรรม การออกและจ่ายรางวัล งานบริหารสาขา (เช่น ปิดสาขาและย้ายข้อมูลไปสาขาปลายทาง) และการส่งข้อมูลออกผ่าน SFTP ไปยังระบบปลายทาง

ลักษณะงานสำคัญ: เป็นระบบที่เกี่ยวกับเงินและสิทธิ์ของลูกค้าโดยตรง — ยอดสลาก การถูกรางวัล การจ่ายเงิน ดังนั้นความถูกต้องของข้อมูลและร่องรอยการตรวจสอบสำคัญกว่าความเร็ว

8ความต่อเนื่อง / DRยังไม่มีไม่มีเครื่องสำรอง ไม่มี RTO/RPO ที่ตกลงกันไว้
9การเฝ้าระวังและแจ้งเตือนยังไม่มีไม่มีการเฝ้าระวังบริการ/ดิสก์/งาน batch และไม่มีการแจ้งเตือน
10ร่องรอยการตรวจสอบบางส่วนยังไม่ชัดว่าเก็บบันทึกใครทำอะไร นานเท่าใด ตามเกณฑ์ตรวจสอบหรือยัง
11การนำระบบขึ้นใช้งานบางส่วนมีคู่มือแต่ทำมือ ไม่มีการเก็บชุดติดตั้งเพื่อย้อนกลับ
12การคุมเวอร์ชันฐานข้อมูลยังไม่มีStored Procedure แก้ที่เครื่องโดยตรง ไม่มีการคุมเวอร์ชัน
13งานส่งข้อมูลออกพร้อมมีสคริปต์ติดตั้งอัตโนมัติ ทำซ้ำได้ + ชุดทดสอบครบ
14ตารางงานอัตโนมัติบางส่วนยังต้องสร้างงานตามเวลาเอง และไม่มีการเฝ้าระวังว่ารันสำเร็จ
15เอกสารระบบบางส่วนมีคู่มือเฉพาะงาน แต่ยังไม่มีเอกสารสถาปัตยกรรม/ปฏิบัติการรวม
16งานย้ายระบบที่ค้างบางส่วนยังมีงานค้างบางรายการที่ยังไม่เริ่ม
ความเสี่ยง

3 เรื่องที่ต้องรีบปิดก่อน

เรียงตามความรุนแรง — ข้อแรกใช้เวลาน้อยที่สุดแต่ลดความเสี่ยงได้มากที่สุด

ความเสี่ยง 01 · สูงมาก

รหัสผ่านเริ่มต้นถูกใช้ซ้ำทุกเครื่องและเก็บไว้ในเอกสาร

บัญชีผู้ดูแลของทั้งเครื่องให้บริการหน้าจอและเครื่องฐานข้อมูล รวมถึงหน้าจอผู้ดูแลของตัวให้บริการเว็บ ใช้รหัสผ่านเริ่มต้นชุดเดียวกัน และถูกบันทึกไว้ในเอกสารที่เปิดอ่านได้

ผลกระทบ: ผู้ที่เข้าถึงเอกสารได้ = เข้าถึงฐานข้อมูลลูกค้าและรายการจ่ายรางวัลได้ทันที เป็นประเด็นที่ผู้ตรวจสอบถือเป็นข้อบกพร่องร้ายแรง

ต้องทำ: เปลี่ยนรหัสผ่านทุกบัญชีทันที · แยกบัญชีรายบุคคล · เลิกใช้บัญชีร่วม · ย้ายความลับไปเก็บในตู้เก็บรหัสผ่านที่ควบคุมสิทธิ์ · ลบรหัสผ่านออกจากเอกสารทั้งหมด
ความเสี่ยง 02 · สูงมาก

ตัวรันโปรแกรมและตัวให้บริการเว็บหมดการสนับสนุน

Java 1.6 สิ้นสุดการสนับสนุนสาธารณะตั้งแต่ปี 2556 · GlassFish รุ่น Java EE 6 ก็ไม่มีผู้ผลิตดูแลแล้ว

ผลกระทบ: ช่องโหว่ที่ค้นพบหลังจากนั้นจะไม่มีแพตช์แก้ตลอดไป และระบบจะไม่ผ่านการสแกนช่องโหว่ ตามมาตรฐานธนาคาร

ต้องทำ: วางแผนยกระดับเป็นรุ่นที่ยังได้รับแพตช์ · ระหว่างที่ยังยกไม่ได้ ให้จำกัดการเข้าถึงเครือข่ายอย่างเข้มงวดเป็นมาตรการชดเชย
ความเสี่ยง 03 · สูงมาก

ไม่มีเครื่องสำรองและยังไม่ได้ตกลงเวลากู้คืน

มีเครื่องให้บริการหน้าจอและเครื่องฐานข้อมูลอย่างละเครื่องเดียว หากเครื่องเสียหาย ระบบจะหยุดจนกว่าจะกู้คืนเสร็จ โดยยังไม่มีข้อตกลงว่าต้องเสร็จภายในกี่ชั่วโมง

ผลกระทบ: หากล่มช่วงออกรางวัลหรือจ่ายรางวัล จะกระทบลูกค้าและชื่อเสียงโดยตรง

ต้องทำ: ตกลงกับเจ้าของระบบว่ายอมให้ระบบหยุดได้นานเท่าใด (RTO) และยอมให้ข้อมูลหายได้ถึงจุดใด (RPO) แล้วออกแบบการสำรอง/เครื่องสำรองให้ได้ตามนั้น
ความเสี่ยงรองลงมา

อีก 7 เรื่องที่ต้องตามแก้

การสำรองข้อมูลยังไม่เป็นระบบ · ไม่มีการเฝ้าระวังและแจ้งเตือน · ตรรกะสำคัญอยู่ใน Stored Procedure โดยไม่มีการคุมเวอร์ชัน · การนำระบบขึ้นใช้งานทำด้วยมือ · งานตามเวลาของการส่งข้อมูลต้องสร้างเองและไม่มีการเฝ้าระวังผล · เอกสารยังไม่รวมศูนย์ทำให้พึ่งพาความรู้ในตัวบุคคล · งานย้ายระบบยังค้างบางรายการ

เป้าหมาย

จากปัจจุบัน สู่เป้าหมาย

ด้านปัจจุบันเป้าหมาย
ความปลอดภัยบัญชีรหัสผ่านชุดเดียวกัน เก็บในเอกสารบัญชีรายบุคคล + เก็บรหัสในระบบที่ควบคุมสิทธิ์
โปรแกรมพื้นฐานหมดระยะการสนับสนุนรุ่นที่ยังได้รับแพตช์ความปลอดภัย
ความต่อเนื่องเครื่องเดียว ไม่มีสำรองมีเครื่องสำรอง ตามเวลากู้คืนที่ตกลง
การสำรองข้อมูลทดสอบครั้งเดียวตอนย้ายระบบสำรองตามตาราง + ซ้อมกู้คืนประจำ มีบันทึกผล
การเฝ้าระวังไม่มี รู้เมื่อผู้ใช้แจ้งเฝ้าระวังอัตโนมัติ + แจ้งเตือนผู้รับผิดชอบ
การแก้ไขระบบแก้ที่เครื่อง ไม่มีประวัติเก็บประวัติทุกการแก้ไข ย้อนกลับได้
การส่งข้อมูลออกตั้งเวลาทำมือ ไม่รู้ผลรันตั้งเวลาอัตโนมัติ + แจ้งเตือนเมื่อไม่สำเร็จ
แผนงาน

แผน 4 เฟส

ระยะเวลาเป็นประมาณการเพื่อใช้หารือ ต้องยืนยันกับเจ้าของระบบและหน่วยงานที่เกี่ยวข้อง

Phase 1
สัปดาห์ 1–2

ปิดความเสี่ยงเร่งด่วน

  • เปลี่ยนรหัสผ่านทุกบัญชีบนทั้งสองเครื่องและหน้าจอผู้ดูแล
  • เลิกใช้บัญชีร่วม — ออกบัญชีรายบุคคลตามบทบาท
  • ลบรหัสผ่านออกจากเอกสารทุกฉบับ ย้ายไปตู้เก็บรหัสที่ควบคุมสิทธิ์
  • จำกัดการเข้าถึงเครือข่ายให้เหลือเท่าที่จำเป็น
  • ทบทวนว่าใครมีสิทธิ์เข้าถึงระบบอยู่บ้างในปัจจุบัน
Phase 2
สัปดาห์ 3–6

ทำให้ดูแลได้จริง

  • ตั้งตารางสำรองข้อมูล + ตรวจสอบไฟล์สำรองอัตโนมัติ
  • ซ้อมกู้คืนจริง 1 ครั้ง จับเวลาเทียบกับเวลากู้คืนที่ตกลง
  • ติดตั้งการเฝ้าระวังและแจ้งเตือน (บริการ ดิสก์ ฐานข้อมูล ผลรันงานส่งข้อมูล)
  • ตั้งงานตามเวลาของการส่งข้อมูลให้เป็นมาตรฐาน + แจ้งเตือนเมื่อไม่สำเร็จ
  • กำหนดนโยบายการเก็บร่องรอยการตรวจสอบ · ปิดงานย้ายระบบที่ค้าง
Phase 3
สัปดาห์ 7–12

คุมการเปลี่ยนแปลง

  • นำโค้ดและ Stored Procedure เข้าระบบควบคุมเวอร์ชัน
  • ใช้การแก้ฐานข้อมูลแบบมีเวอร์ชัน แทนการแก้ที่เครื่องโดยตรง
  • จัดทำขั้นตอนนำระบบขึ้นใช้งานมาตรฐาน + เก็บชุดติดตั้งเพื่อย้อนกลับ
  • จัดทำเอกสารสถาปัตยกรรม + คู่มือปฏิบัติการรวมศูนย์
  • กำหนดขั้นตอนการขอเปลี่ยนแปลงและผู้อนุมัติ
Phase 4
ประเมินหลัง Phase 3

ยกระดับโปรแกรมพื้นฐาน

  • ประเมินทางเลือก: ยกระดับระบบเดิม หรือ พัฒนาใหม่
  • วิเคราะห์ผลกระทบ ค่าใช้จ่าย และระยะเวลาของแต่ละทาง
  • เสนอเจ้าของระบบตัดสินใจเลือกแนวทาง
สิ่งที่ต้องได้คำตอบ

ประเด็นที่ต้องให้เจ้าของระบบตัดสินใจ

ประเด็นทำไมต้องรู้
1ระบบใช้งานช่วงเวลาใด และช่วงไหนห้ามหยุดกำหนดช่วงเวลาเปลี่ยนแปลงและแผนกู้คืน
2ยอมให้ระบบหยุดได้นานเท่าใด (RTO)ออกแบบเครื่องสำรองและขั้นตอนกู้คืน — บล็อก Phase 2
3ยอมให้ข้อมูลหายได้ถึงจุดใด (RPO)กำหนดความถี่การสำรองข้อมูล — บล็อก Phase 2
4ต้องเก็บข้อมูลและบันทึกย้อนหลังกี่ปีกำหนดพื้นที่จัดเก็บและนโยบาย
5ผู้ใช้งานกี่คน สาขาหรือส่วนกลางประเมินขนาดเครื่องและสิทธิ์การเข้าถึง
6ระบบปลายทางของการส่งข้อมูลคือระบบใด ใครดูแลกำหนดผู้ประสานงานและระดับบริการที่ตกลง
7ใครคือผู้อนุมัติการเปลี่ยนแปลงระบบตั้งขั้นตอนการขอเปลี่ยนแปลง
8ใครดูแลระบบหลังใช้งานจริง และช่วงเวลาใดกำหนดรูปแบบการสนับสนุน
9งบประมาณและกรอบเวลาสำหรับ Phase 4เลือกระหว่างยกระดับกับพัฒนาใหม่ — บล็อก Phase 4
10มีข้อกำหนดจากผู้กำกับหรือผู้ตรวจสอบเพิ่มหรือไม่ปรับแผนให้สอดคล้อง

ข้อเสนอแนะ
1แยกสองเรื่องออกจากกันให้ชัด — ทำให้ระบบ Production ปัจจุบันมั่นคง (เร่งด่วน) กับ การพัฒนาระบบใหม่ในอนาคต อย่ารวมเป็นแผนเดียวเพราะความเร่งด่วนต่างกัน
2เริ่มจากความปลอดภัยของบัญชีและรหัสผ่านทันที — ใช้เวลาน้อย ต้นทุนต่ำ แต่ลดความเสี่ยงได้มากที่สุด
3ต้องได้ตัวเลข RTO/RPO จากเจ้าของระบบก่อน จึงจะออกแบบการสำรองและเครื่องสำรองได้อย่างมีเหตุผล
4ยอมรับตามตรงว่าโปรแกรมพื้นฐานหมดการสนับสนุน และเสนอเป็นแผนระยะกลาง ไม่ควรปล่อยไว้เฉย ๆ
5ต่อยอดของดีที่มีอยู่ — งานส่งข้อมูลออกทำมาตรฐานได้ดีแล้ว (สคริปต์ทำซ้ำได้ + ชุดทดสอบครบ) ใช้เป็นต้นแบบกับงานอื่น

เอกสารฉบับร่างเพื่อใช้หารือกับเจ้าของระบบ · ตัวเลขระยะเวลาและข้อสรุปทุกข้อรอการยืนยันจากผู้เกี่ยวข้อง · รายละเอียดทางเทคนิคเพิ่มเติมอยู่ในเอกสารโครงการ · เอกสารนี้ไม่มีรหัสผ่านหรือความลับของระบบโดยเจตนา
