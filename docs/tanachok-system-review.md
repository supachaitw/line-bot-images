## บทสรุปผู้บริหาร

**สถานะ:** สลากธนโชค **ปิดการขายแล้ว** เหลือเพียงรอผู้ถือสลากมาถอน ระบบจึงอยู่ใน
**โหมดจ่ายคืน (Run-off)** — เป้าหมายเปลี่ยนจาก "ให้บริการต่อเนื่อง" เป็น
**"จ่ายคืนให้ครบ แล้วปิดระบบ"**

พร้อมกันนั้น **มีมติย้ายแพลตฟอร์มแล้ว** — จาก Windows Server + MS SQL Server + Java/GlassFish
ไปเป็น **Linux (Ubuntu) + Docker + PostgreSQL** ระบบใหม่อยู่ระหว่างเตรียมการ ยังไม่ขึ้นใช้งานจริง

**ข้อค้นพบหลัก 4 ข้อ**

1. **มีสองงานใหญ่ทับซ้อนกัน** — ระบบกำลังจะปิด (run-off) และกำลังย้ายแพลตฟอร์มไปพร้อมกัน
   ทั้งสองอย่างแย่งทรัพยากรและมีความเสี่ยงคนละแบบ ต้องวางลำดับให้ชัด
2. **ความเสี่ยงใหญ่ที่สุดย้ายไปอยู่ที่การย้ายข้อมูล** — MS SQL → PostgreSQL หมายถึง
   ต้องเขียน Stored Procedure ทั้งชุดใหม่ และต้องพิสูจน์ว่า **ยอดเงินของลูกค้าตรงทุกบาท**
   ข้อผิดพลาดตรงนี้กระทบเงินลูกค้าโดยตรง
3. **ขอบเขตงานลดลงมาก** — จาก 21 ฟังก์ชัน เหลือที่ต้องดูแลจริง **8 รายการ**
   ตัดออกได้ 7 และรอเจ้าของระบบตัดสินใจ 6 → **ย้ายเฉพาะ 8 รายการนี้ก็พอ ไม่ต้องยกไปทั้งระบบ**
4. **ความเสี่ยงด้านความปลอดภัยยังต้องแก้ทันทีบนระบบเดิม** — การย้ายแพลตฟอร์มใช้เวลาหลายเดือน
   ระหว่างนั้นข้อมูลลูกค้ายังอยู่บนระบบเดิมที่รหัสผ่านยังใช้ซ้ำกันและเก็บไว้ในเอกสาร

**สิ่งที่ควรทำทันที:** เปลี่ยนรหัสผ่านทุกบัญชีและลบรหัสผ่านออกจากเอกสาร (Phase 1)
ทำบนระบบเดิม ไม่ต้องรอการย้ายแพลตฟอร์ม — ใช้เวลาน้อย ต้นทุนต่ำ ลดความเสี่ยงได้มากที่สุด

**สิ่งที่ประหยัดได้:** **ย้ายเฉพาะ 8 ฟังก์ชันที่ยังใช้จริง** ไม่ต้องยกงานขาย งานออกรางวัลงวดใหม่
และรายงานยอดขายไปด้วย — ลดทั้งงานเขียน Stored Procedure ใหม่และงานทดสอบลงอย่างมาก

**คำถามเชิงกลยุทธ์ที่ควรตอบให้ชัด:** ระบบกำลังจะปิดอยู่แล้ว — **การย้ายแพลตฟอร์มคุ้มกับ
ความเสี่ยงการย้ายข้อมูลเงินลูกค้าหรือไม่** หรือควรคงระบบเดิมพร้อมมาตรการชดเชยจนถึงวันปิด
คำตอบขึ้นกับว่าอีกกี่ปีจึงจะปิดได้ และมีข้อบังคับอะไรที่ทำให้อยู่บนแพลตฟอร์มเดิมต่อไม่ได้

**คำตอบที่ต้องได้จากเจ้าของระบบ:** เหลือผู้ถือกี่ราย ยอดเท่าไร · มีกำหนดวันปิดระบบหรือยัง ·
ปลายทาง Feed ยังต้องการข้อมูลไหม · ยอดจ่ายคืนคิดอย่างไร · เงินที่ไม่มีผู้มาถอนจัดการตามระเบียบใด

## 1. ระบบคืออะไร

**ธนโชค** คือระบบงานสลากออมสิน รองรับงานหลัก:
- ข้อมูลผู้ถือสลาก / ลูกค้า (`PDCUST`)
- ทะเบียนสลากหลัก (`PDMAST`) และการอ้างอิงข้าม (`PDXREF`)
- รายการธุรกรรม (`PDTRN`)
- การออกรางวัลและจ่ายรางวัล (`PDRPZ`, `PDRPMISS`, `PRIZEAMT`, `PDTRAN_PRIZEAMT`)
- งานบริหารสาขา เช่น **ปิดสาขาและย้ายข้อมูลไปสาขาปลายทาง**
  (มีคู่มือเฉพาะ + ชุด Stored Procedure `dbo.spl_UPDATE_*`)
- **ส่งข้อมูลออกผ่าน SFTP Feed** ไปยังปลายทางภายนอก (งาน FTP_FEED_PROD)

**ลักษณะงาน:** เกี่ยวกับ **เงินและสิทธิ์ของลูกค้าโดยตรง** — ยอดสลาก การถูกรางวัล การจ่ายเงิน
ดังนั้น **ความถูกต้องของข้อมูลและร่องรอยการตรวจสอบสำคัญกว่าความเร็ว** และในโหมดจ่ายคืน
ความสำคัญของร่องรอยการตรวจสอบยิ่งสูงขึ้น เพราะเป็นหลักฐานว่าจ่ายคืนใครไปแล้วบ้าง

## 2. สถาปัตยกรรม — ปัจจุบันและปลายทาง

### 2.1 ระบบที่ใช้งานอยู่วันนี้ (AS IS)

```
            ผู้ใช้งาน (สาขา / ส่วนกลาง)
                       │
                       ▼
     ┌─────────────────────────────────┐
     │  Web App Server                 │   Windows Server 2019
     │                                 │   Java 1.6 + GlassFish (Java EE 6)
     └───────────────┬─────────────────┘
                     │ JDBC
                     ▼
     ┌─────────────────────────────────┐
     │  Database Server                │   Windows Server 2019
     │                                 │   MS SQL Server 2019
     │  Stored Procedures = ตรรกะหลัก   │
     └───────────────┬─────────────────┘
                     │
                     ▼
        SFTP Feed → ระบบปลายทางภายนอก
```

**ข้อสังเกต**
- เป็น **2-tier แบบเครื่องละตัว** ทั้ง Web และ DB — ไม่มี cluster/failover
- **ตรรกะธุรกิจจำนวนมากอยู่ใน Stored Procedure** (`dbo.spl_UPDATE_PDCUST`, `PDMAST`,
  `PDTRN`, `PDRPZ`, `PDXREF`, `PRIZEAMT`, `getrunning` ฯลฯ) → เป็นจุดที่ย้ายยากที่สุด
- SFTP Feed มีสคริปต์ติดตั้งที่ทำซ้ำได้ (idempotent) + ชุดทดสอบ TC-01…TC-09

### 2.2 แพลตฟอร์มปลายทางที่ยืนยันแล้ว (TO BE)

**มีมติย้ายแพลตฟอร์มแล้ว** ปลายทางคือ **Linux (Ubuntu) + Docker + PostgreSQL**
โครงระบบใหม่ประกอบด้วยบริการที่แยกกันเป็น container:

| บริการ | บทบาท |
|---|---|
| `tanachok-gateway` | ทางเข้าระบบ (nginx) |
| `tanachok-web` | หน้าจอผู้ใช้ |
| `tanachok-api` | ประมวลผลหลัก (แทนที่ตรรกะที่เคยอยู่ใน Stored Procedure) |
| `tanachok-pdf` | ออกเอกสาร PDF |
| `tanachok-postgres` | **ฐานข้อมูล PostgreSQL** (แทน MS SQL Server) |
| `tanachok-adminer` | เครื่องมือดูแลฐานข้อมูล |

**สถานะปัจจุบันของระบบใหม่:** อยู่บนเครื่องพัฒนา ยังไม่ขึ้นใช้งานจริง และยัง **ไม่ได้เปิดรัน**

**หลักฐานที่สอดคล้อง:** งาน SFTP Feed เตรียมสคริปต์ติดตั้งไว้ **ทั้งฉบับ Windows (`.bat`)
และฉบับ Linux/Unix (`.sh`)** — สอดคล้องกับการเตรียมย้ายแพลตฟอร์ม

> **หมายเหตุเรื่องเอกสาร:** หน้า TANACHOK ใน Notion (แก้ล่าสุดต้นเดือน ส.ค. 2569)
> ยังบันทึกสถาปัตยกรรมเป็น Windows + MS SQL อยู่ — **ควรอัปเดตให้ตรงกับมติย้ายแพลตฟอร์ม**
> เพื่อไม่ให้ผู้อ่านคนถัดไปสับสนแบบเดียวกัน

### 2.3 สิ่งที่การย้ายแพลตฟอร์มทำให้เปลี่ยน

| ด้าน | ผลจากการย้าย |
|---|---|
| รันไทม์หมดการสนับสนุน (Java 1.6 / GlassFish) | **แก้ที่ต้นเหตุ** — ไม่ต้องใช้มาตรการชดเชยระยะยาว |
| ตรรกะใน Stored Procedure | **ต้องเขียนใหม่ทั้งชุด** — T-SQL ย้ายไป PostgreSQL ตรง ๆ ไม่ได้ |
| ข้อมูลลูกค้าและยอดเงิน | **ต้องย้ายและพิสูจน์ความถูกต้องทุกบาท** — ความเสี่ยงสูงสุดของทั้งโครงการ |
| งาน SFTP Feed | ต้องเปลี่ยนจากงานตามเวลาแบบ Windows ไปเป็นแบบ Linux (สคริปต์เตรียมไว้แล้ว) |
| ค่าลิขสิทธิ์ Windows / MS SQL | ลดลงหลัง cutover |
| ขอบเขตที่ต้องย้าย | **ย้ายเฉพาะ 8 ฟังก์ชันในกลุ่ม A** ที่ยังใช้จริง (ดูส่วนที่ 3) |

## 3. ขอบเขตที่เหลือหลังปิดการขาย

ทบทวนฟังก์ชันทั้งหมด **21 รายการ** แบ่งเป็น 3 กลุ่ม

### 3.1 คงไว้ — 8 ฟังก์ชัน (ขอบเขตขั้นต่ำจนกว่าจะปิดระบบ)

| # | ฟังก์ชัน | ทำไมต้องคงไว้ |
|---|---|---|
| A1 | ค้นหาผู้ถือสลาก | จุดเริ่มต้นของทุกเคสเมื่อลูกค้าเดินเข้าสาขา |
| A2 | แสดงยอดคงเหลือและสิทธิ์ที่พึงได้รับ | ต้องรู้ว่าจ่ายคืนเท่าไร (เงินต้น + สิทธิ์ค้างจ่าย) |
| A3 | บันทึกการถอน/จ่ายคืน | ธุรกรรมประเภทเดียวที่ยังเกิดขึ้นจริง |
| A4 | ตรวจเงินรางวัลค้างจ่าย | ผู้ถือยังมีสิทธิ์รับรางวัลงวดเก่าที่ยังไม่ได้ขึ้นเงิน |
| A5 | ประวัติธุรกรรมรายผู้ถือสลาก | หลักฐานการจ่ายคืน ใช้ตอบข้อโต้แย้งและการตรวจสอบ |
| A6 | รายงานยอดคงค้างทั้งระบบ | ฝ่ายบัญชีต้องรู้ภาระผูกพันที่เหลือ และใช้ติดตามความคืบหน้า |
| A7 | งานปิด/ย้ายสาขา | สาขาทยอยปิด ต้องย้ายข้อมูลผู้ถือไปสาขาปลายทาง |
| A8 | จัดการผู้ใช้และสิทธิ์เข้าถึง | ควบคุมว่าใครจ่ายเงินได้ ใครดูข้อมูลได้ |

### 3.2 ตัดออก — 7 ฟังก์ชัน

| # | ฟังก์ชัน | เหตุผล | วิธีจัดการ |
|---|---|---|---|
| B1 | ขาย/ซื้อสลากใหม่ | ไม่เปิดขายแล้ว | ปิดเมนู + ปิดสิทธิ์ |

## 4. ประเมินความพร้อม 16 ด้าน (ของระบบเดิมที่ยังใช้งานอยู่)

ระดับ: **พร้อม** / **บางส่วน** / **ยังไม่มี** — คอลัมน์สุดท้ายคือความเร่งด่วน **หลังปิดการขาย**

| # | ด้าน | ระดับ | สาระสำคัญ | ความเร่งด่วนในโหมดจ่ายคืน |
|---|---|---|---|---|
| 1 | เซิร์ฟเวอร์ & OS | **พร้อม** | ย้ายขึ้น Windows Server 2019 แล้วทั้งสองเครื่อง | — |
| 2 | ฐานข้อมูล | **พร้อม** | MS SQL Server 2019 ติดตั้งแล้ว + ทดสอบกู้คืนสำเร็จ | — |
| 3 | Runtime (Java) | **ยังไม่มี** | หมดการสนับสนุนตั้งแต่ปี 2556 ไม่มี security patch | **แก้ด้วยการย้ายแพลตฟอร์ม** — ระหว่างรอใช้มาตรการชดเชย |
| 4 | Application Server | **ยังไม่มี** | หมดการสนับสนุน ไม่มีผู้ผลิตดูแล | **แก้ด้วยการย้ายแพลตฟอร์ม** — เช่นเดียวกับข้อ 3 |
| 5 | การจัดการรหัสผ่าน | **ยังไม่มี** | ใช้รหัสผ่านเริ่มต้นชุดเดียวกันทุกเครื่อง + เก็บในเอกสาร | **สูงสุด — ไม่เปลี่ยน** |
| 6 | สิทธิ์การเข้าถึง | **บางส่วน** | ยังใช้บัญชีร่วมกัน ไม่มีบัญชีรายบุคคล | **สูง — ไม่เปลี่ยน** |
| 7 | การสำรองข้อมูล | **บางส่วน** | ทดสอบครั้งเดียวตอนย้าย ยังไม่มีตารางสำรองประจำ | **สูงขึ้น** — ต้องเป็นจุดย้อนกลับก่อนย้ายข้อมูล |
| 8 | DR / ความต่อเนื่อง | **ยังไม่มี** | ไม่มีเครื่องสำรอง ไม่มี RTO/RPO ที่ตกลงไว้ | **ลดลง** — ธุรกรรมต่ำ ยอมให้ RTO ยาวขึ้นได้ |
| 9 | การเฝ้าระวังและแจ้งเตือน | **ยังไม่มี** | ระบบล่มจะรู้เมื่อผู้ใช้แจ้ง | **ลดลง** — เหลือเท่าที่จำเป็น |
| 10 | ร่องรอยการตรวจสอบ | **บางส่วน** | ยังไม่ชัดว่าเก็บอะไร นานเท่าใด | **สูงขึ้น** — เป็นหลักฐานการจ่ายคืน |
| 11 | การนำระบบขึ้นใช้งาน | **บางส่วน** | มีคู่มือแต่ทำมือ ย้อนกลับยาก | **ลดลงมาก** — แทบไม่มี deploy แล้ว |
| 12 | การคุมเวอร์ชันฐานข้อมูล | **ยังไม่มี** | Stored Procedure แก้ที่เครื่อง ไม่มีเวอร์ชัน | **สูงขึ้น** — ต้องคุมเวอร์ชันตอนเขียนใหม่บน PostgreSQL |
| 13 | งานส่งข้อมูลออก (Feed) | **พร้อม** | script ติดตั้งอัตโนมัติ + ชุดทดสอบครบ · มีฉบับ Linux แล้ว | **ขึ้นกับ C2** — อาจตัดทิ้งทั้งชุด |
| 14 | ตารางงานอัตโนมัติ | **บางส่วน** | ต้องสร้างงานตามเวลาเอง ไม่มีการเฝ้าระวังผล | **ขึ้นกับ C2** |
| 15 | เอกสารระบบ | **บางส่วน** | มีคู่มือเฉพาะงาน ยังไม่รวมศูนย์ | **สูงขึ้น** — ป้องกันความรู้ผูกกับตัวบุคคลช่วงปิดระบบ |
| 16 | งานย้ายระบบที่ค้าง | **บางส่วน** | ยังมีงานค้างบางรายการ | คงเดิม |

**สรุป:** พร้อม 3 · บางส่วน 7 · ยังไม่มี 6 → **ระบบเดิมยังไม่ควรถือว่าพร้อม Production เต็มรูปแบบ**

เมื่อรวมกับมติย้ายแพลตฟอร์ม แบ่งการลงทุนได้เป็น 3 กลุ่ม:
- **ทำทันทีบนระบบเดิม (รอไม่ได้):** รหัสผ่าน · สิทธิ์เข้าถึง · สำรองข้อมูล · ร่องรอยตรวจสอบ
- **แก้ที่ต้นเหตุด้วยการย้าย (ไม่ต้องลงทุนบนระบบเดิม):** รันไทม์ · ตัวให้บริการเว็บ
- **ต้องทำใหม่บนแพลตฟอร์มใหม่:** การคุมเวอร์ชันฐานข้อมูล · การเฝ้าระวัง · การนำระบบขึ้นใช้งาน

## 5. ความเสี่ยง

### 🔴 สูงมาก — ต้องจัดการก่อน

**R1. รหัสผ่านเริ่มต้นถูกใช้ซ้ำทุกเครื่องและเก็บไว้ในเอกสาร**
บัญชีผู้ดูแลของทั้ง Web Server และ DB Server รวมถึงหน้าจอผู้ดูแลของตัวให้บริการเว็บ
ใช้รหัสผ่านเริ่มต้นชุดเดียวกัน และถูกบันทึกไว้ในเอกสารที่เปิดอ่านได้
- **ผลกระทบ:** ผู้ที่เข้าถึงเอกสารได้ = เข้าถึงฐานข้อมูลลูกค้าและรายการจ่ายเงินได้ทันที
  เป็นข้อบกพร่องร้ายแรงในสายตาผู้ตรวจสอบ
- **ต้องทำ:** เปลี่ยนรหัสผ่านทุกบัญชีทันที **บนระบบเดิม ไม่ต้องรอการย้ายแพลตฟอร์ม** ·
  แยกบัญชีรายบุคคล · ลบรหัสผ่านออกจากเอกสาร · และ**อย่ายกวิธีตั้งรหัสแบบเดิมไปแพลตฟอร์มใหม่**

**R2. การย้ายข้อมูลจาก MS SQL ไป PostgreSQL — ความเสี่ยงสูงสุดของโครงการ**
ตรรกะธุรกิจจำนวนมากอยู่ใน Stored Procedure ของ MS SQL (`spl_UPDATE_PDCUST`, `PDMAST`,
`PDTRN`, `PDRPZ`, `PDXREF`, `PRIZEAMT`, `getrunning` ฯลฯ) ซึ่ง **ย้ายไป PostgreSQL ตรง ๆ ไม่ได้**
ต้องเขียนใหม่และพิสูจน์ว่าให้ผลเหมือนเดิม
- **ผลกระทบ:** ระบบนี้เก็บ **ยอดเงินและสิทธิ์ของลูกค้า** หากคำนวณเพี้ยนแม้เล็กน้อย
  จะกลายเป็นจ่ายคืนผิดจำนวน ซึ่งแก้ย้อนหลังยากและกระทบความเชื่อมั่นโดยตรง
- **ต้องทำ:** เขียน Stored Procedure ใหม่เฉพาะที่ยังใช้จริง (กลุ่ม A) · ทำ **การกระทบยอด
  (reconciliation) ทุกบัญชีทุกบาท** ระหว่างระบบเก่ากับใหม่ · **รันคู่ขนาน (parallel run)**
  เทียบผลอย่างน้อย 1 รอบเต็มก่อน cutover · มีแผนย้อนกลับหากผลไม่ตรง

**R3. ความถูกต้องของภาษาไทยและชนิดข้อมูลหลังย้ายฐานข้อมูล**
ชื่อ-ที่อยู่ลูกค้าเป็นภาษาไทย การย้ายข้ามชนิดฐานข้อมูลมักเจอปัญหา encoding/collation
และความต่างของชนิดข้อมูลตัวเลขทศนิยม
- **ผลกระทบ:** ชื่อลูกค้าเพี้ยน ค้นหาไม่เจอ หรือยอดเงินปัดเศษต่างจากเดิม
- **ต้องทำ:** กำหนด encoding เป็น UTF-8 ตั้งแต่ต้น · ตรวจตัวอย่างข้อมูลจริงที่มีสระ/วรรณยุกต์ ·
  ใช้ชนิดข้อมูลตัวเลขที่ไม่ปัดเศษสำหรับจำนวนเงิน

**R4. ทำสองงานใหญ่พร้อมกันบนทีมเดียว**
ระบบกำลังปิดตัว (run-off) และย้ายแพลตฟอร์มไปพร้อมกัน ขณะที่สาขาก็ทยอยปิด
- **ผลกระทบ:** ทรัพยากรถูกแบ่ง งานใดงานหนึ่งอาจค้างกลางทาง และช่วง cutover
  เป็นช่วงที่เสี่ยงที่สุดสำหรับลูกค้าที่มาถอน
- **ต้องทำ:** เรียงลำดับให้ชัด — **ความปลอดภัยก่อน · ย้ายแพลตฟอร์มทีหลัง** ·
  หลีกเลี่ยง cutover ช่วงที่มีผู้มาถอนหนาแน่น

### 🟠 สูง

**R5. รันไทม์เดิมยังหมดการสนับสนุนตลอดช่วงที่ยังไม่ย้ายเสร็จ**
Java 1.6 / GlassFish ไม่มีแพตช์ความปลอดภัยแล้ว และการย้ายแพลตฟอร์มใช้เวลาหลายเดือน
→ ระหว่างนี้ต้อง **จำกัดการเข้าถึงเครือข่ายอย่างเข้มงวด** และบันทึกเป็นข้อยกเว้นที่อนุมัติแล้ว
พร้อมกำหนดวันสิ้นสุดที่ผูกกับแผน cutover

**R6. การสำรองข้อมูลยังไม่เป็นระบบ** — ทดสอบกู้คืนครั้งเดียวตอนย้ายเครื่อง
ยังไม่มีตารางสำรองประจำ **และยิ่งสำคัญขึ้นเมื่อจะย้ายฐานข้อมูล** เพราะต้องมีจุดย้อนกลับที่เชื่อถือได้
→ ต้องมีตารางสำรอง + ซ้อมกู้คืนพร้อมบันทึกผล **ก่อนเริ่มย้ายข้อมูล**

**R7. ร่องรอยการตรวจสอบต้องไม่ขาดตอนตรงรอยต่อ**
ในโหมดจ่ายคืน ร่องรอยคือหลักฐานว่าจ่ายเงินให้ใครไปแล้ว หากย้ายระบบแล้วประวัติเดิมค้นไม่ได้
จะตอบข้อโต้แย้งและผู้ตรวจสอบไม่ได้
→ ต้องยกประวัติธุรกรรมเดิมไปด้วย และทดสอบว่าค้นย้อนหลังได้จริงหลังย้าย

**R8. ความรู้ผูกกับตัวบุคคล** — เอกสารกระจายตามงาน ไม่มีคู่มือปฏิบัติการรวมศูนย์
ช่วงย้ายแพลตฟอร์มและปิดระบบมักมีการโยกย้ายคน ทำให้เสี่ยงกว่าปกติ

### 🟡 ปานกลาง

**R9. ไม่มีเครื่องสำรอง** — ในโหมดจ่ายคืนผลกระทบต่ำลง แต่ยังต้องตกลงเวลากู้คืนที่ยอมรับได้
**R10. การเฝ้าระวังยังไม่มี** — ควรมีพื้นฐาน (บริการ ดิสก์ ฐานข้อมูล) และต้องเตรียมไว้บนแพลตฟอร์มใหม่ด้วย
**R11. งาน Feed ต้องย้ายไป Linux** — สคริปต์ `.sh` เตรียมไว้แล้ว แต่ยังไม่ได้ทดสอบบนสภาพแวดล้อมจริง
**R12. เอกสาร Notion ยังบันทึกสถาปัตยกรรมเก่า** — ควรอัปเดตให้ตรงมติ ป้องกันคนอ่านเข้าใจผิด

## 7. แผนงาน 5 เฟส

> ระยะเวลาเป็นประมาณการเพื่อใช้หารือ ต้องยืนยันกับเจ้าของระบบและหน่วยงานที่เกี่ยวข้อง
> **หลักการเรียงลำดับ: ความปลอดภัยก่อน · ย้ายแพลตฟอร์มทีหลัง** เพราะการย้ายใช้เวลาหลายเดือน
> แต่ความเสี่ยงด้านรหัสผ่านรอไม่ได้

### Phase 1 — ปิดความเสี่ยงเร่งด่วนบนระบบเดิม (สัปดาห์ 1–2)
- [ ] เปลี่ยนรหัสผ่านทุกบัญชีบน Web/DB Server และหน้าจอผู้ดูแล
- [ ] เลิกใช้บัญชีร่วม — ออกบัญชีรายบุคคลตามบทบาท
- [ ] ลบรหัสผ่านออกจากเอกสารทุกฉบับ ย้ายไปตู้เก็บรหัสที่ควบคุมสิทธิ์
- [ ] จำกัดการเข้าถึงเครือข่ายให้เหลือเท่าที่จำเป็น (มาตรการชดเชยของ R5 จนกว่าจะ cutover)
- [ ] **ปิดเมนูและปิดสิทธิ์ฟังก์ชันกลุ่ม B ทั้ง 7 รายการ** (ห้ามลบข้อมูล)
      — ทำก่อนย้าย เพื่อไม่ต้องยกงานที่เลิกใช้ไปแพลตฟอร์มใหม่

### Phase 2 — ทำให้ดูแลได้จริงและเตรียมจุดย้อนกลับ (สัปดาห์ 3–6)
- [ ] ตั้งตารางสำรองข้อมูล + ตรวจสอบไฟล์สำรองอัตโนมัติ
- [ ] **ซ้อมกู้คืนจริง 1 ครั้ง** — ต้องผ่านก่อนเริ่มย้ายข้อมูลใน Phase 3
- [ ] กำหนดนโยบายการเก็บร่องรอยการตรวจสอบ
- [ ] ติดตั้งการเฝ้าระวังพื้นฐาน (บริการ ดิสก์ ฐานข้อมูล)
- [ ] **ตัดสินใจเรื่อง Feed (C2)** — ถ้าเลิกส่ง ตัดงานนี้ออกจากขอบเขตการย้ายไปเลย

### Phase 3 — เตรียมย้ายแพลตฟอร์ม (สัปดาห์ 7–16) · งานหนักที่สุด
- [ ] ยืนยันขอบเขตที่จะย้าย = **เฉพาะ 8 ฟังก์ชันกลุ่ม A**
- [ ] เขียน Stored Procedure ที่ยังใช้จริงใหม่บน PostgreSQL
- [ ] ย้ายโครงสร้างข้อมูลและข้อมูลจริง พร้อมกำหนด encoding ภาษาไทยและชนิดข้อมูลจำนวนเงิน
- [ ] **ทำการกระทบยอด (reconciliation) ทุกบัญชีทุกบาท** เทียบระบบเก่า–ใหม่
- [ ] ยกประวัติธุรกรรมเดิมไปด้วย และทดสอบว่าค้นย้อนหลังได้จริง
- [ ] ย้ายงาน Feed ไปสคริปต์ฉบับ Linux + ทดสอบตามชุด TC เดิม (ถ้ายังต้องส่ง)
- [ ] นำโค้ดและสคริปต์ย้ายข้อมูลเข้าระบบควบคุมเวอร์ชัน + จัดทำคู่มือปฏิบัติการ

### Phase 4 — รันคู่ขนานและ Cutover
- [ ] **รันคู่ขนาน (parallel run)** อย่างน้อย 1 รอบเต็ม เทียบผลระบบเก่า–ใหม่
- [ ] ให้ผู้ใช้จริงทดสอบการจ่ายคืนบนระบบใหม่ (UAT)
- [ ] กำหนดเกณฑ์ผ่าน/ไม่ผ่าน และ **แผนย้อนกลับหากยอดไม่ตรง**
- [ ] เลือกช่วงเวลา cutover ที่มีผู้มาถอนน้อย + แจ้งสาขาล่วงหน้า
- [ ] cutover แล้วเฝ้าระวังใกล้ชิดในช่วงแรก
- [ ] ปลดระวางเครื่อง Windows เดิมหลังยืนยันว่าระบบใหม่นิ่งแล้ว

### Phase 5 — แผนปิดระบบ · รอกำหนดวัน
- [ ] กำหนดวันสิ้นสุดการรับคำขอถอน และแจ้งผู้ถือสลากล่วงหน้า
- [ ] กำหนดวิธีจัดการยอดที่ไม่มีผู้มาถอนตามระเบียบ
- [ ] วางแผนเก็บข้อมูลถาวร (archive) ให้ค้นย้อนหลังได้หลังปิดระบบ
- [ ] กำหนดวิธีให้บริการหากมีผู้มาติดต่อหลังปิดระบบ
- [ ] ปลดระวางระบบและเพิกถอนสิทธิ์เข้าถึงทั้งหมด

> **ข้อสังเกตเชิงกลยุทธ์:** Phase 3–4 เป็นงานหนักและมีความเสี่ยงเรื่องเงินลูกค้า
> ขณะที่ Phase 5 คือการปิดระบบอยู่ดี **ถ้าวันปิดระบบอยู่ใกล้พอ อาจคุ้มกว่าที่จะคงระบบเดิม
> พร้อมมาตรการชดเชยจนถึงวันปิด แทนการย้ายแพลตฟอร์ม** — ควรตัดสินใจข้อนี้ก่อนเริ่ม Phase 3

## 8. หน้าจอที่เสนอ

ตัวอย่างหน้าจอ 3 หน้า (ดู `docs/tanachok-mockups.html`) ปรับให้ตรงขอบเขตที่เหลือ:

| หน้าจอ | สาระสำคัญ |
|---|---|
| **1 · ภาพรวมการจ่ายคืน** | ยอดคงค้างรอจ่ายคืน · จ่ายคืนวันนี้ · เงินรางวัลค้างจ่าย · ความคืบหน้าการปิด + อัตราการมาถอนรายเดือน |
| **2 · ค้นหาผู้ถือสลาก และจ่ายคืน** | หน้าจอสำคัญที่สุด — ค้นหา ตรวจยอดที่ต้องจ่าย (แยกเงินต้น/รางวัลค้างจ่าย/ผลตอบแทน) แล้วบันทึกการจ่ายคืนจบในหน้าเดียว |
| **3 · รายงานความคืบหน้าการจ่ายคืน** | ยอดคงค้างแยกตามสาขา + ประมาณการว่าอีกกี่ปีจะปิดระบบได้ |

**หลักการออกแบบที่ใช้:** เมนูที่ปิดแล้ว (ขายสลาก ฝากเพิ่ม ตรวจรางวัลงวดใหม่) ยังแสดงแบบจางขีดฆ่า
เพื่อให้ผู้ใช้เข้าใจว่า **ปิดโดยตั้งใจ ไม่ใช่ระบบเสีย** และรายการธุรกรรมเก่าคงไว้พร้อมทำเครื่องหมาย
"รายการเดิม" — ข้อมูลไม่ถูกลบ แต่ผู้ใช้รู้ว่าทำรายการแบบนั้นใหม่ไม่ได้แล้ว

## 10. ข้อเสนอแนะสรุป

1. **เริ่ม Phase 1 ทันทีบนระบบเดิม** — อย่ารอการย้ายแพลตฟอร์ม เพราะการย้ายใช้เวลาหลายเดือน
   ระหว่างนั้นข้อมูลลูกค้ายังอยู่บนระบบที่รหัสผ่านใช้ซ้ำกันและเก็บไว้ในเอกสาร
2. **ตัดสินใจข้อ 1 ในตารางก่อนเริ่ม Phase 3** — ระบบกำลังจะปิดอยู่แล้ว
   ถ้าวันปิดอยู่ใกล้พอ การคงระบบเดิมพร้อมมาตรการชดเชยอาจเสี่ยงน้อยกว่าและถูกกว่า
   การย้ายฐานข้อมูลที่เก็บยอดเงินลูกค้า
3. **ถ้าย้าย — ย้ายเฉพาะ 8 ฟังก์ชันกลุ่ม A** และปิดกลุ่ม B ก่อนย้าย
   จะลดงานเขียน Stored Procedure ใหม่และงานทดสอบลงอย่างมาก
4. **การกระทบยอดคือหัวใจ ไม่ใช่การย้ายให้เสร็จ** — ต้องรันคู่ขนานเทียบผลอย่างน้อย 1 รอบเต็ม
   และมีแผนย้อนกลับที่ใช้ได้จริง ก่อนตัดสินใจ cutover
5. **ซ้อมกู้คืนให้ผ่านก่อนแตะข้อมูล** — เป็นจุดย้อนกลับเดียวที่มีถ้าการย้ายผิดพลาด
6. **อัปเดตเอกสารใน Notion ให้ตรงมติย้ายแพลตฟอร์ม** — ตอนนี้ยังบันทึกเป็น
   Windows + MS SQL ทำให้ผู้อ่านเข้าใจผิดได้ (เกิดขึ้นแล้วในการจัดทำเอกสารชุดนี้)
7. **ต่อยอดของดีที่มีอยู่** — งาน SFTP Feed ทำมาตรฐานได้ดีและเตรียมสคริปต์ฉบับ Linux ไว้แล้ว
   ใช้เป็นต้นแบบของงานย้ายส่วนอื่น
