## บทสรุปผู้บริหาร

**สถานะ:** สลากธนโชค **ปิดการขายแล้ว** เหลือเพียงรอผู้ถือสลากมาถอน ระบบจึงอยู่ใน
**โหมดจ่ายคืน (Run-off)** — เป้าหมายเปลี่ยนจาก "ให้บริการต่อเนื่อง" เป็น
**"จ่ายคืนให้ครบ แล้วปิดระบบ"**

**ข้อค้นพบหลัก 4 ข้อ**

1. **แผนเดิมเขียนผิดระบบ** — ฉบับก่อนหน้าอ้างอิง stack นักพัฒนาในเครื่อง (Docker)
   ระบบจริงคือ Windows Server 2019 สองเครื่อง + Java 1.6 + GlassFish + MS SQL Server 2019
2. **ยังไม่ควรถือว่าพร้อม Production เต็มรูปแบบ** — ประเมิน 16 ด้าน ได้ พร้อม 3 · บางส่วน 7 · ยังไม่มี 6
   โครงสร้างพื้นฐานย้ายเครื่องใหม่เรียบร้อยแล้ว แต่ยังขาดด้านความปลอดภัย ความต่อเนื่อง และการเฝ้าระวัง
3. **ขอบเขตงานลดลงมาก** — จาก 21 ฟังก์ชัน เหลือที่ต้องดูแลจริง **8 รายการ**
   ตัดออกได้ 7 และรอเจ้าของระบบตัดสินใจ 6
4. **ความเสี่ยงด้านความปลอดภัยไม่ได้ลดลงเลย** — ปิดการขายไม่ได้ทำให้ข้อมูลลูกค้าและเงิน
   ที่ยังอยู่ในระบบปลอดภัยขึ้น และผู้ตรวจสอบยังตรวจระบบที่ยังมีข้อมูลอยู่

**สิ่งที่ควรทำทันที:** เปลี่ยนรหัสผ่านทุกบัญชีและลบรหัสผ่านออกจากเอกสาร (Phase 1)
เป็นงานที่ใช้เวลาน้อย ต้นทุนต่ำ แต่ลดความเสี่ยงได้มากที่สุด และ **เริ่มได้ทันทีโดยไม่ต้องรอคำตอบข้ออื่น**

**สิ่งที่ประหยัดได้:** ยกเลิก Phase 4 (ยกระดับรันไทม์/พัฒนาใหม่) ทั้งเฟส —
ไม่คุ้มที่จะรื้อระบบที่กำลังจะปิด

**คำตอบที่ต้องได้จากเจ้าของระบบ:** ปลายทาง Feed ยังต้องการข้อมูลไหม · มีกำหนดวันปิดระบบหรือยัง ·
เหลือผู้ถือกี่ราย ยอดเท่าไร · ยอดจ่ายคืนคิดอย่างไร · เงินที่ไม่มีผู้มาถอนจัดการตามระเบียบใด

## 1. ระบบคืออะไร

**ธนโชค** คือระบบงานสลากออมสิน รองรับงานหลัก:
- ข้อมูลผู้ถือสลาก / ลูกค้า (`PDCUST`)
- ทะเบียนสลากหลัก (`PDMAST`) และการอ้างอิงข้าม (`PDXREF`)
- รายการธุรกรรม (`PDTRN`)
- การออกรางวัลและจ่ายรางวัล (`PDRPZ`, `PDRPMISS`, `PRIZEAMT`, `PDTRAN_PRIZEAMT`)
- งานบริหารสาขา เช่น **ปิดสาขาและย้ายข้อมูลไปสาขาปลายทาง**
  (มีคู่มือเฉพาะ + ชุด Stored Procedure `dbo.spl_UPDATE_*`)
- **ส่งข้อมูลออกผ่าน SFTP Feed** ไปยังปลายทางภายนอก (งาน FTP_FEED_PROD)

**ลักษณะงาน:** เกี่ยวกับ **เงินและสิทธิ์ของลูกค้าโดยตรง** — ยอดสลาก การถูกรางวัล การจ่ายเงิน
ดังนั้น **ความถูกต้องของข้อมูลและร่องรอยการตรวจสอบสำคัญกว่าความเร็ว** และในโหมดจ่ายคืน
ความสำคัญของร่องรอยการตรวจสอบยิ่งสูงขึ้น เพราะเป็นหลักฐานว่าจ่ายคืนใครไปแล้วบ้าง

## 2. สถาปัตยกรรมปัจจุบัน (AS IS)

```
            ผู้ใช้งาน (สาขา / ส่วนกลาง)
                       │
                       ▼
     ┌─────────────────────────────────┐
     │  Web App Server                 │   Windows Server 2019
     │                                 │   Java 1.6 + GlassFish (Java EE 6)
     └───────────────┬─────────────────┘
                     │ JDBC
                     ▼
     ┌─────────────────────────────────┐
     │  Database Server                │   Windows Server 2019
     │                                 │   MS SQL Server 2019
     │  Stored Procedures = ตรรกะหลัก   │
     └───────────────┬─────────────────┘
                     │
                     ▼
        SFTP Feed → ระบบปลายทางภายนอก
```

**ข้อสังเกต**
- เป็น **2-tier แบบเครื่องละตัว** ทั้ง Web และ DB — ไม่มี cluster/failover
- **ตรรกะธุรกิจจำนวนมากอยู่ใน Stored Procedure** → เปลี่ยนแปลงยาก ทดสอบยาก
  ติดตามเวอร์ชันไม่ได้ถ้าไม่คุมด้วยเครื่องมือ
- SFTP Feed เป็นงาน batch แยก มี script ติดตั้งที่ทำซ้ำได้ (idempotent) + ชุดทดสอบ
  TC-01…TC-09 — **จุดนี้ทำมาตรฐานได้ดี ใช้เป็นต้นแบบกับงานอื่นได้**

### ข้อแก้ไขจากแผนฉบับแรก

| หัวข้อ | ฉบับแรก (คลาดเคลื่อน) | ข้อเท็จจริง |
|---|---|---|
| แพลตฟอร์ม | Linux + Docker | **Windows Server 2019** (2 เครื่อง) |
| ภาษา/รันไทม์ | ไม่ระบุ | **Java 1.6** |
| Application Server | nginx + Node | **GlassFish (Java EE 6)** |
| ฐานข้อมูล | PostgreSQL | **MS SQL Server 2019** |
| เหตุผลที่ต้องย้ายเครื่อง | ยังไม่ระบุ | **OS และฐานข้อมูลเดิมหมดระยะสนับสนุน** |

> `tanachok-next` (Docker stack ที่อ้างในฉบับแรก) เป็นงานทดลอง/ต่อยอดคนละเรื่อง
> **ไม่ใช่ระบบ Production** — และในโหมดจ่ายคืนก็ไม่ควรลงทุนต่อแล้ว

## 3. ขอบเขตที่เหลือหลังปิดการขาย

| A4 | ตรวจเงินรางวัลค้างจ่าย | ผู้ถือยังมีสิทธิ์รับรางวัลงวดเก่าที่ยังไม่ได้ขึ้นเงิน |
| A5 | ประวัติธุรกรรมรายผู้ถือสลาก | หลักฐานการจ่ายคืน ใช้ตอบข้อโต้แย้งและการตรวจสอบ |

| A8 | จัดการผู้ใช้และสิทธิ์เข้าถึง | ควบคุมว่าใครจ่ายเงินได้ ใครดูข้อมูลได้ |

## 4. ประเมินความพร้อม 16 ด้าน (ปรับน้ำหนักตามโหมดจ่ายคืน)

ระดับ: **พร้อม** / **บางส่วน** / **ยังไม่มี** — คอลัมน์สุดท้ายคือความเร่งด่วน **หลังปิดการขาย**

| # | ด้าน | ระดับ | สาระสำคัญ | ความเร่งด่วนในโหมดจ่ายคืน |
|---|---|---|---|---|
| 1 | เซิร์ฟเวอร์ & OS | **พร้อม** | ย้ายขึ้น Windows Server 2019 แล้วทั้งสองเครื่อง | — |
| 2 | ฐานข้อมูล | **พร้อม** | MS SQL Server 2019 ติดตั้งแล้ว + ทดสอบกู้คืนสำเร็จ | — |
| 3 | Runtime (Java) | **ยังไม่มี** | หมดการสนับสนุนตั้งแต่ปี 2556 ไม่มี security patch | **ลดลง** — ใช้มาตรการชดเชยแทนการยกระดับ |
| 4 | Application Server | **ยังไม่มี** | หมดการสนับสนุน ไม่มีผู้ผลิตดูแล | **ลดลง** — เช่นเดียวกับข้อ 3 |
| 5 | การจัดการรหัสผ่าน | **ยังไม่มี** | ใช้รหัสผ่านเริ่มต้นชุดเดียวกันทุกเครื่อง + เก็บในเอกสาร | **สูงสุด — ไม่เปลี่ยน** |
| 6 | สิทธิ์การเข้าถึง | **บางส่วน** | ยังใช้บัญชีร่วมกัน ไม่มีบัญชีรายบุคคล | **สูง — ไม่เปลี่ยน** |
| 7 | การสำรองข้อมูล | **บางส่วน** | ทดสอบครั้งเดียวตอนย้าย ยังไม่มีตารางสำรองประจำ | **สูง — ไม่เปลี่ยน** |
| 8 | DR / ความต่อเนื่อง | **ยังไม่มี** | ไม่มีเครื่องสำรอง ไม่มี RTO/RPO ที่ตกลงไว้ | **ลดลง** — ธุรกรรมต่ำ ยอมให้ RTO ยาวขึ้นได้ |
| 9 | การเฝ้าระวังและแจ้งเตือน | **ยังไม่มี** | ระบบล่มจะรู้เมื่อผู้ใช้แจ้ง | **ลดลง** — เหลือเท่าที่จำเป็น |
| 10 | ร่องรอยการตรวจสอบ | **บางส่วน** | ยังไม่ชัดว่าเก็บอะไร นานเท่าใด | **สูงขึ้น** — เป็นหลักฐานการจ่ายคืน |
| 11 | การนำระบบขึ้นใช้งาน | **บางส่วน** | มีคู่มือแต่ทำมือ ย้อนกลับยาก | **ลดลงมาก** — แทบไม่มี deploy แล้ว |
| 12 | การคุมเวอร์ชันฐานข้อมูล | **ยังไม่มี** | Stored Procedure แก้ที่เครื่อง ไม่มีเวอร์ชัน | **ลดลง** — เหลือเพียงคุมสิทธิ์การแก้ไข |
| 13 | งานส่งข้อมูลออก (Feed) | **พร้อม** | script ติดตั้งอัตโนมัติ + ชุดทดสอบครบ | **ขึ้นกับ C2** — อาจตัดทิ้งทั้งชุด |
| 14 | ตารางงานอัตโนมัติ | **บางส่วน** | ต้องสร้างงานตามเวลาเอง ไม่มีการเฝ้าระวังผล | **ขึ้นกับ C2** |
| 15 | เอกสารระบบ | **บางส่วน** | มีคู่มือเฉพาะงาน ยังไม่รวมศูนย์ | **สูงขึ้น** — ป้องกันความรู้ผูกกับตัวบุคคลช่วงปิดระบบ |
| 16 | งานย้ายระบบที่ค้าง | **บางส่วน** | ยังมีงานค้างบางรายการ | คงเดิม |

**สรุป:** พร้อม 3 · บางส่วน 7 · ยังไม่มี 6 → **ยังไม่ควรถือว่าพร้อม Production เต็มรูปแบบ**
แต่ในโหมดจ่ายคืน **สิ่งที่ต้องเร่งเหลือเพียงกลุ่มความปลอดภัยและร่องรอยการตรวจสอบ**
ส่วนงานสถาปัตยกรรม CI/CD และ HA ลดความสำคัญลงอย่างมีนัยสำคัญ

## 5. ความเสี่ยง

### 🔴 สูงมาก — ต้องปิดก่อน

**R1. รหัสผ่านเริ่มต้นถูกใช้ซ้ำทุกเครื่องและเก็บไว้ในเอกสาร**
บัญชีผู้ดูแลของทั้ง Web Server และ DB Server รวมถึงหน้าจอผู้ดูแลของตัวให้บริการเว็บ
ใช้รหัสผ่านเริ่มต้นชุดเดียวกัน และถูกบันทึกไว้ในเอกสารที่เปิดอ่านได้
- **ผลกระทบ:** ผู้ที่เข้าถึงเอกสารได้ = เข้าถึงฐานข้อมูลลูกค้าและรายการจ่ายเงินได้ทันที
  เป็นข้อบกพร่องร้ายแรงในสายตาผู้ตรวจสอบ
- **ต้องทำ:** เปลี่ยนรหัสผ่านทุกบัญชีทันที · แยกบัญชีรายบุคคล · เลิกใช้บัญชีร่วม ·
  ย้ายความลับไปเก็บในตู้เก็บรหัสผ่านที่ควบคุมสิทธิ์ · ลบรหัสผ่านออกจากเอกสารทั้งหมด

**R2. รันไทม์และตัวให้บริการเว็บหมดการสนับสนุน**
Java 1.6 สิ้นสุดการสนับสนุนตั้งแต่ปี 2556 · GlassFish รุ่น Java EE 6 ไม่มีผู้ผลิตดูแลแล้ว
- **ผลกระทบ:** ช่องโหว่ที่พบใหม่จะไม่มีแพตช์แก้ และไม่ผ่านการสแกนตามมาตรฐานธนาคาร
- **ต้องทำ (ปรับตามโหมดจ่ายคืน):** **ไม่ยกระดับรันไทม์** เพราะไม่คุ้มกับอายุที่เหลือของระบบ
  ให้ใช้ **มาตรการชดเชย** แทน — จำกัดการเข้าถึงเครือข่ายอย่างเข้มงวด ให้เข้าถึงได้เฉพาะ
  เครื่องและผู้ใช้ที่จำเป็น และบันทึกเป็นข้อยกเว้นที่ได้รับอนุมัติพร้อมกำหนดวันสิ้นสุด

**R3. ไม่มีเครื่องสำรองและยังไม่ได้ตกลงเวลากู้คืน**
มีเครื่องละหนึ่งตัว หากเสียหายระบบจะหยุดจนกว่าจะกู้คืนเสร็จ
- **ผลกระทบ:** ในโหมดจ่ายคืนผลกระทบต่ำลง (ลูกค้ามาถอนไม่ใช่งานเร่งด่วนรายนาที)
  แต่ยังต้องมีเวลากู้คืนที่ตกลงกันไว้ ไม่ใช่ปล่อยไม่กำหนด
- **ต้องทำ:** ตกลง **RTO/RPO** ที่ยอมรับได้ในบริบทนี้ แล้วออกแบบการสำรองให้ได้ตามนั้น
  (อาจไม่ต้องมีเครื่องสำรองพร้อมใช้ แต่ต้องมีขั้นตอนกู้คืนที่ซ้อมแล้ว)

### 🟠 สูง

**R4. การสำรองข้อมูลยังไม่เป็นระบบ** — ทดสอบกู้คืนครั้งเดียวตอนย้ายเครื่อง
ยังไม่มีตารางสำรองประจำ ไม่มีการตรวจว่าไฟล์สำรองใช้ได้จริง
→ ต้องมีตารางสำรอง + ซ้อมกู้คืนพร้อมบันทึกผล

**R5. ร่องรอยการตรวจสอบยังไม่ชัดเจน** — ในโหมดจ่ายคืนนี่คือหลักฐานว่าจ่ายเงินให้ใครไปแล้ว
→ ต้องกำหนดว่าเก็บอะไร ระบุตัวผู้ทำรายการได้ และเก็บนานเท่าใด

**R6. ความรู้ผูกกับตัวบุคคล** — เอกสารกระจายตามงาน ไม่มีคู่มือปฏิบัติการรวมศูนย์
ช่วงปิดระบบมักมีการโยกย้ายคน ทำให้เสี่ยงกว่าปกติ
→ จัดทำคู่มือปฏิบัติการรวมศูนย์

### 🟡 ปานกลาง

**R7. การเฝ้าระวังยังไม่มี** — ลดระดับลงได้ แต่ควรมีการเฝ้าระวังพื้นฐาน (บริการ ดิสก์ ฐานข้อมูล)
**R8. งาน Feed ต้องสร้างงานตามเวลาเองและไม่รู้ผลรัน** — ขึ้นกับการตัดสินใจ C2
**R9. ตรรกะอยู่ใน Stored Procedure โดยไม่มีการคุมเวอร์ชัน** — ลดระดับลง เหลือเพียงคุมสิทธิ์การแก้ไข
**R10. งานย้ายระบบยังค้างบางรายการ** — ควรปิดให้จบเพื่อไม่ให้เป็นภาระค้าง

## 6. AS IS → TO BE

|---|---|---|

| ความปลอดภัยบัญชี | รหัสผ่านชุดเดียวกัน เก็บในเอกสาร | บัญชีรายบุคคล + เก็บรหัสในระบบที่ควบคุมสิทธิ์ |
| รันไทม์ที่หมดการสนับสนุน | ไม่มีมาตรการรองรับ | จำกัดการเข้าถึงเป็นมาตรการชดเชย + บันทึกเป็นข้อยกเว้นที่อนุมัติแล้ว |
| ความต่อเนื่อง | เครื่องเดียว ไม่มีข้อตกลงเวลากู้คืน | มีขั้นตอนกู้คืนที่ซ้อมแล้ว ตาม RTO/RPO ที่ตกลง |
| การสำรองข้อมูล | ทดสอบครั้งเดียวตอนย้ายเครื่อง | สำรองตามตาราง + ซ้อมกู้คืนประจำ มีบันทึกผล |
| ร่องรอยการตรวจสอบ | ไม่ชัดเจน | เก็บครบ ระบุตัวผู้ทำรายการได้ ตรวจย้อนหลังได้ |
| การส่งข้อมูลออก | ตั้งเวลาทำมือ ไม่รู้ผลรัน | ตั้งเวลาอัตโนมัติ + แจ้งเตือน **หรือยกเลิกทั้งชุด** ตาม C2 |
| เอกสาร | กระจายตามงาน | คู่มือปฏิบัติการรวมศูนย์ |
| ปลายทางของระบบ | ไม่มีแผนปิด | มีวันปิดระบบ วิธีจัดการยอดค้าง และแผนเก็บข้อมูลถาวร |

## 7. แผนงาน 5 เฟส

> ระยะเวลาเป็นประมาณการเพื่อใช้หารือ ต้องยืนยันกับเจ้าของระบบและหน่วยงานที่เกี่ยวข้อง

### Phase 1 — ปิดความเสี่ยงเร่งด่วน (สัปดาห์ 1–2) · คงไว้เต็มรูปแบบ
- [ ] เปลี่ยนรหัสผ่านทุกบัญชีบน Web/DB Server และหน้าจอผู้ดูแล
- [ ] เลิกใช้บัญชีร่วม — ออกบัญชีรายบุคคลตามบทบาท
- [ ] ลบรหัสผ่านออกจากเอกสารทุกฉบับ ย้ายไปตู้เก็บรหัสที่ควบคุมสิทธิ์
- [ ] จำกัดการเข้าถึงเครือข่ายให้เหลือเท่าที่จำเป็น (มาตรการชดเชยของ R2)
- [ ] ทบทวนว่าใครมีสิทธิ์เข้าถึงระบบอยู่บ้างในปัจจุบัน
- [ ] **ปิดเมนูและปิดสิทธิ์ฟังก์ชันกลุ่ม B ทั้ง 7 รายการ** (ห้ามลบข้อมูล)

### Phase 2 — ทำให้ดูแลได้จริง (สัปดาห์ 3–6) · ลดขนาดจากแผนเดิม
- [ ] ตั้งตารางสำรองข้อมูล + ตรวจสอบไฟล์สำรองอัตโนมัติ
- [ ] ซ้อมกู้คืนจริง 1 ครั้ง จับเวลาเทียบกับ RTO ที่ตกลง
- [ ] กำหนดนโยบายการเก็บร่องรอยการตรวจสอบ (สำคัญขึ้นในโหมดนี้)
- [ ] ติดตั้งการเฝ้าระวังพื้นฐาน (บริการ ดิสก์ ฐานข้อมูล) — ลดขอบเขตจากแผนเดิม
- [ ] ปิดงานย้ายระบบที่ยังค้าง
- [ ] **งาน Feed: ตั้งงานตามเวลา + เฝ้าระวัง หรือยกเลิกทั้งชุด** — รอคำตอบ C2

### Phase 3 — คุมการเปลี่ยนแปลง (สัปดาห์ 7–12) · เหลือเท่าที่จำเป็น
- [ ] คุมสิทธิ์การแก้ไขระบบและฐานข้อมูล
- [ ] นำ Stored Procedure ที่ยังใช้งานเข้าระบบควบคุมเวอร์ชัน
- [ ] จัดทำคู่มือปฏิบัติการรวมศูนย์ + กำหนดผู้อนุมัติการเปลี่ยนแปลง

### ~~Phase 4 — ยกระดับรันไทม์ / พัฒนาใหม่~~ · **ยกเลิกทั้งเฟส**
ไม่คุ้มที่จะรื้อระบบที่กำลังจะปิด — **เป็นการประหยัดที่ใหญ่ที่สุดจากเงื่อนไขใหม่นี้**
ความเสี่ยงจากรันไทม์เก่าให้จัดการด้วยมาตรการชดเชยใน Phase 1 แทน

### Phase 5 — แผนปิดระบบ (ใหม่) · รอกำหนดวัน
- [ ] กำหนดวันสิ้นสุดการรับคำขอถอน และแจ้งผู้ถือสลากล่วงหน้า
- [ ] กำหนดวิธีจัดการยอดที่ไม่มีผู้มาถอนตามระเบียบ
- [ ] วางแผนเก็บข้อมูลถาวร (archive) ให้ค้นย้อนหลังได้หลังปิดระบบ
- [ ] กำหนดวิธีให้บริการหากมีผู้มาติดต่อหลังปิดระบบ
- [ ] ปลดระวางเครื่องและเพิกถอนสิทธิ์เข้าถึงทั้งหมด

## 8. หน้าจอที่เสนอ

ตัวอย่างหน้าจอ 3 หน้า (ดู `docs/tanachok-mockups.html`) ปรับให้ตรงขอบเขตที่เหลือ:

| หน้าจอ | สาระสำคัญ |
|---|---|
| **1 · ภาพรวมการจ่ายคืน** | ยอดคงค้างรอจ่ายคืน · จ่ายคืนวันนี้ · เงินรางวัลค้างจ่าย · ความคืบหน้าการปิด + อัตราการมาถอนรายเดือน |
| **2 · ค้นหาผู้ถือสลาก และจ่ายคืน** | หน้าจอสำคัญที่สุด — ค้นหา ตรวจยอดที่ต้องจ่าย (แยกเงินต้น/รางวัลค้างจ่าย/ผลตอบแทน) แล้วบันทึกการจ่ายคืนจบในหน้าเดียว |
| **3 · รายงานความคืบหน้าการจ่ายคืน** | ยอดคงค้างแยกตามสาขา + ประมาณการว่าอีกกี่ปีจะปิดระบบได้ |

**หลักการออกแบบที่ใช้:** เมนูที่ปิดแล้ว (ขายสลาก ฝากเพิ่ม ตรวจรางวัลงวดใหม่) ยังแสดงแบบจางขีดฆ่า
เพื่อให้ผู้ใช้เข้าใจว่า **ปิดโดยตั้งใจ ไม่ใช่ระบบเสีย** และรายการธุรกรรมเก่าคงไว้พร้อมทำเครื่องหมาย
"รายการเดิม" — ข้อมูลไม่ถูกลบ แต่ผู้ใช้รู้ว่าทำรายการแบบนั้นใหม่ไม่ได้แล้ว

## 10. ข้อเสนอแนะสรุป

1. **เริ่ม Phase 1 ทันที** — ไม่ต้องรอคำตอบข้ออื่น เป็นงานที่ใช้เวลาน้อย ต้นทุนต่ำ
   แต่ลดความเสี่ยงได้มากที่สุด และเป็นสิ่งที่ผู้ตรวจสอบมองหาเป็นอันดับแรก
2. **ลดขอบเขตให้เหลือ 8 ฟังก์ชัน และปิดกลุ่ม B ทันที** — ลดพื้นที่เสี่ยง ลดความสับสนของผู้ใช้
   และลดงานดูแล โดย **ห้ามลบข้อมูล**
3. **ยกเลิก Phase 4** — การประหยัดที่ใหญ่ที่สุด และเปลี่ยนวิธีจัดการความเสี่ยงรันไทม์
   จาก "ยกระดับ" เป็น "จำกัดการเข้าถึง + บันทึกเป็นข้อยกเว้นที่อนุมัติแล้ว"
4. **เร่งถามเรื่อง Feed (ข้อ 1)** — จุดเดียวที่ตัดแล้วประหยัดงานได้มากที่สุดทันที
5. **เริ่มคุยเรื่องวันปิดระบบตั้งแต่ตอนนี้** — เป็นตัวกำหนดทุกอย่างที่เหลือ
   และเป็นงานที่ต้องใช้เวลาประสานหลายฝ่าย
6. **ต่อยอดของดีที่มีอยู่** — งาน SFTP Feed ทำมาตรฐานได้ดี (สคริปต์ทำซ้ำได้ + ชุดทดสอบครบ)
   ใช้เป็นต้นแบบกับงานอื่น เช่น การสำรองข้อมูลและการกู้คืน
