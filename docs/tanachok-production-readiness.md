## 1. ระบบคืออะไร (ภาพธุรกิจ)

**ธนโชค** คือระบบงานสลาก (สลากออมสิน) รองรับงานหลัก:
- ข้อมูลผู้ถือสลาก / ลูกค้า (`PDCUST`)
- ทะเบียนสลากหลัก (`PDMAST`) และการอ้างอิงข้าม (`PDXREF`)
- รายการธุรกรรม (`PDTRN`)
- การออกรางวัลและจ่ายรางวัล (`PDRPZ`, `PDRPMISS`, `PRIZEAMT`, `PDTRAN_PRIZEAMT`)
- งานบริหารสาขา เช่น **ปิดสาขาและย้ายข้อมูลไปสาขาปลายทาง** (มีคู่มือเฉพาะ + ชุด
  Stored Procedure `dbo.spl_UPDATE_*`)
- **ส่งข้อมูลออกผ่าน SFTP Feed** ไปยังปลายทางภายนอก (งาน FTP_FEED_PROD)

**ลักษณะงาน:** เป็นระบบที่เกี่ยวกับ **เงินและสิทธิ์ของลูกค้าโดยตรง** (ยอดสลาก, การถูกรางวัล,
การจ่ายเงิน) → ความถูกต้องของข้อมูลและร่องรอยการตรวจสอบมีความสำคัญสูงกว่าความเร็ว

## 2. สถาปัตยกรรมปัจจุบัน (AS IS)

```
            ผู้ใช้งาน (สาขา / ส่วนกลาง)
                       │
                       ▼
     ┌─────────────────────────────────┐
     │  Web App Server                 │   Thanachok.App  (10.22.251.21)
     │  Windows Server 2019            │   Java 1.6 + GlassFish (Java EE 6)
     └───────────────┬─────────────────┘
                     │ JDBC
                     ▼
     ┌─────────────────────────────────┐
     │  Database Server                │   Thanachok.DB   (10.22.253.21)
     │  Windows Server 2019            │   MS SQL Server 2019
     │  Stored Procedures = ตรรกะหลัก   │
     └───────────────┬─────────────────┘
                     │
                     ▼
        SFTP Feed → ระบบปลายทางภายนอก
        (D:\TANACHOK\FTP_FEED, key-based auth)
```

**ข้อสังเกตเชิงสถาปัตยกรรม**
- เป็น **2-tier แบบ single instance** ทั้ง Web และ DB — ไม่มี cluster/failover
- **ตรรกะธุรกิจจำนวนมากอยู่ใน Stored Procedure** → เปลี่ยนแปลงยาก ทดสอบยาก
  ติดตามเวอร์ชันไม่ได้ถ้าไม่คุมด้วยเครื่องมือ
- SFTP Feed เป็นงาน batch แยก มี script ติดตั้งที่ทำได้ซ้ำ (idempotent) + มีชุดทดสอบ
  TC-01…TC-09 — **จุดนี้ทำมาดี**

## 4. ความเสี่ยงสำคัญ (เรียงตามความรุนแรง)

### 🔴 สูงมาก — ควรแก้ก่อนอื่น

**R1. รหัสผ่านเริ่มต้นถูกใช้ซ้ำทุกเครื่องและเก็บเป็นข้อความธรรมดา**
- พบว่าบัญชี Administrator และ admin ของทั้ง Web Server และ DB Server รวมถึง
  หน้าจอผู้ดูแล GlassFish ใช้ **รหัสผ่านเริ่มต้นชุดเดียวกัน** และถูกบันทึกไว้ใน
  เอกสารที่เปิดอ่านได้
- **ผลกระทบ:** ผู้ที่เข้าถึงเอกสารได้ = เข้าถึงฐานข้อมูลลูกค้าและรายการจ่ายรางวัลได้ทันที
  เป็นประเด็นที่ผู้ตรวจสอบ (ITGC/ผู้กำกับ) ถือเป็นข้อบกพร่องร้ายแรง
- **สิ่งที่ต้องทำ:** เปลี่ยนรหัสผ่านทุกบัญชีทันที · แยกบัญชีรายบุคคล · เลิกใช้บัญชีร่วม ·
  ย้ายความลับไปเก็บใน secret store/ตู้เก็บรหัสผ่าน · ลบรหัสผ่านออกจากเอกสารทั้งหมด

**R2. Java 1.6 และ GlassFish หมดการสนับสนุน**
- Java 1.6 สิ้นสุดการสนับสนุนสาธารณะตั้งแต่ปี 2013 · GlassFish รุ่น Java EE 6 ก็ไม่มีผู้ผลิตดูแลแล้ว
- **ผลกระทบ:** ช่องโหว่ที่ค้นพบหลังจากนั้นจะ **ไม่มีแพตช์แก้** ตลอดไป และระบบจะไม่ผ่าน
  การสแกนช่องโหว่ตามมาตรฐานธนาคาร
- **สิ่งที่ต้องทำ:** วางแผนยกระดับรันไทม์ (Java 11/17 LTS + application server ที่ยังมีการดูแล)
  ระหว่างที่ยังยกไม่ได้ ให้จำกัดการเข้าถึงเครือข่ายอย่างเข้มงวดเป็นมาตรการชดเชย

**R3. ไม่มีเครื่องสำรองและยังไม่ได้ตกลง RTO/RPO**
- Web และ DB อย่างละเครื่องเดียว หากเครื่องเสียหาย = ระบบหยุดจนกว่าจะกู้เสร็จ
- **ผลกระทบ:** ช่วงออกรางวัล/จ่ายรางวัลหากระบบล่ม จะกระทบลูกค้าและชื่อเสียงโดยตรง
- **สิ่งที่ต้องทำ:** ตกลงกับเจ้าของระบบว่า **ยอมให้ระบบหยุดได้นานเท่าใด (RTO)** และ
  **ยอมให้ข้อมูลหายได้ถึงจุดใด (RPO)** แล้วออกแบบการสำรอง/เครื่องสำรองให้ได้ตามนั้น

### 🟠 สูง

**R4. การสำรองข้อมูลยังไม่เป็นระบบ** — เคยทดสอบ restore ครั้งเดียวตอนย้ายเครื่อง
ยังไม่มีตารางสำรองประจำ ไม่มีการตรวจว่าไฟล์สำรองใช้ได้จริง และไม่มีการซ้อมกู้คืน
→ **ต้องมีตารางสำรอง + ทดสอบกู้คืนอย่างน้อยปีละครั้งพร้อมบันทึกผล**

**R5. ไม่มีการเฝ้าระวังและแจ้งเตือน** — ถ้าบริการหยุด ดิสก์เต็ม หรือ Feed ไม่ทำงาน
จะรู้ก็ต่อเมื่อผู้ใช้แจ้ง → **ต้องมี monitoring + alert ส่งถึงผู้รับผิดชอบ**

**R6. ตรรกะสำคัญอยู่ใน Stored Procedure โดยไม่มีการคุมเวอร์ชัน** — การแก้ที่เครื่องโดยตรง
ทำให้ย้อนกลับไม่ได้และตรวจสอบไม่ได้ว่าใครแก้อะไรเมื่อไหร่
→ **นำ SP เข้าระบบควบคุมเวอร์ชัน + ใช้ versioned migration**

### 🟡 ปานกลาง

**R7. Deploy ด้วยมือ** — เสี่ยงทำข้ามขั้น/ทำไม่เหมือนกันแต่ละครั้ง และย้อนกลับยาก
**R8. งาน Scheduled Task ของ Feed ต้องสร้างมือและไม่มีการเฝ้าระวังผลลัพธ์**
**R9. เอกสารสถาปัตยกรรม/ปฏิบัติการยังไม่รวมศูนย์** — พึ่งพาความรู้ในตัวบุคคล
**R10. งานย้ายระบบยังค้างบางรายการ** — เช่นการติดตั้งฝั่ง DB Server ที่ยังไม่เริ่ม

## 5. AS IS → TO BE

| ด้าน | AS IS (ปัจจุบัน) | TO BE (เป้าหมาย Production) |
|---|---|---|
| รหัสผ่าน/ความลับ | ใช้รหัสเริ่มต้นชุดเดียวกัน เก็บในเอกสาร | บัญชีรายบุคคล + เก็บความลับใน secret store |
| Runtime | Java 1.6 (หมดการสนับสนุน) | Java LTS ที่ยังได้รับแพตช์ |
| App Server | GlassFish Java EE 6 (หมดการสนับสนุน) | Application server ที่ยังมีผู้ผลิตดูแล |
| ความต่อเนื่อง | เครื่องเดียว ไม่มีสำรอง | มีเครื่อง/เส้นทางสำรอง ตาม RTO/RPO ที่ตกลง |
| การสำรองข้อมูล | ทดสอบครั้งเดียวตอนย้าย | สำรองตามตาราง + ซ้อมกู้คืนประจำ มีบันทึกผล |
| การเฝ้าระวัง | ไม่มี | monitoring + alert ครอบคลุมบริการ/ดิสก์/งาน batch |
| Audit log | ไม่ชัดเจน | เก็บครบตามเกณฑ์ ระบุตัวผู้ใช้ได้ ตรวจสอบย้อนหลังได้ |
| การ Deploy | ทำมือตามคู่มือ | มีขั้นตอนมาตรฐาน + เก็บ artifact ย้อนกลับได้ |
| Stored Procedure | แก้ที่เครื่อง ไม่มีเวอร์ชัน | อยู่ใน source control + versioned migration |
| SFTP Feed | script ติดตั้งพร้อม แต่ task สร้างมือ | ติดตั้ง+ตั้งเวลาอัตโนมัติ + เฝ้าระวังผลรัน |
| เอกสาร | กระจายตามงาน | เอกสารสถาปัตยกรรม + คู่มือปฏิบัติการรวมศูนย์ |

## 6. แผนงานเสนอ (4 เฟส)

> ระยะเวลาเป็น **ประมาณการเพื่อใช้หารือ** ต้องยืนยันกับเจ้าของระบบและหน่วยงานที่เกี่ยวข้อง

### Phase 1 — ปิดความเสี่ยงเร่งด่วน (สัปดาห์ที่ 1–2)
- [ ] เปลี่ยนรหัสผ่านทุกบัญชีบน Web/DB Server และหน้าจอผู้ดูแล
- [ ] เลิกใช้บัญชีร่วม → ออกบัญชีรายบุคคลตามบทบาท
- [ ] ลบรหัสผ่านออกจากเอกสารทุกฉบับ ย้ายไปตู้เก็บรหัสผ่านที่ควบคุมสิทธิ์
- [ ] จำกัดการเข้าถึงเครือข่ายของทั้งสองเครื่องให้เหลือเท่าที่จำเป็น
- [ ] ทบทวนว่าใครมีสิทธิ์เข้าถึงระบบอยู่บ้างในปัจจุบัน

### Phase 2 — ทำให้ดูแลได้จริง (สัปดาห์ที่ 3–6)
- [ ] ตั้งตารางสำรองข้อมูล + ตรวจสอบไฟล์สำรองอัตโนมัติ
- [ ] ซ้อมกู้คืนจริง 1 ครั้ง พร้อมจับเวลาเทียบกับ RTO ที่ตกลง
- [ ] ติดตั้ง monitoring + alert (บริการ, ดิสก์, ฐานข้อมูล, ผลรัน Feed)
- [ ] ตั้ง Scheduled Task ของ Feed ให้เป็นมาตรฐาน + แจ้งเตือนเมื่อรันไม่สำเร็จ
- [ ] ตรวจสอบและกำหนดนโยบายการเก็บ audit log
- [ ] ปิดงานย้ายระบบที่ยังค้าง

### Phase 3 — คุมการเปลี่ยนแปลง (สัปดาห์ที่ 7–12)
- [ ] นำ source code และ Stored Procedure เข้าระบบควบคุมเวอร์ชัน
- [ ] ใช้ versioned migration สำหรับการแก้ฐานข้อมูล
- [ ] จัดทำขั้นตอน deploy มาตรฐาน + เก็บ artifact เพื่อย้อนกลับได้
- [ ] จัดทำเอกสารสถาปัตยกรรม + คู่มือปฏิบัติการรวมศูนย์
- [ ] กำหนดขั้นตอนการขอเปลี่ยนแปลง (change) และผู้อนุมัติ

### Phase 4 — ยกระดับรันไทม์ (ประเมินหลังจบ Phase 3)

## 7. สิ่งที่ต้องให้เจ้าของระบบยืนยัน/ตัดสินใจ

| # | ประเด็น | ทำไมต้องรู้ |
|---|---|---|
| 1 | ระบบใช้งานช่วงเวลาใด และช่วงไหนห้ามหยุด | กำหนด change window และแผน DR |
| 2 | **ยอมให้ระบบหยุดได้นานเท่าใด (RTO)** | ออกแบบเครื่องสำรอง/ขั้นตอนกู้คืน |
| 3 | **ยอมให้ข้อมูลหายได้ถึงจุดใด (RPO)** | กำหนดความถี่การสำรองข้อมูล |
| 4 | ต้องเก็บข้อมูล/log ย้อนหลังกี่ปี | กำหนดพื้นที่จัดเก็บและนโยบาย |
| 5 | ผู้ใช้งานกี่คน สาขา/ส่วนกลาง | ประเมินขนาดเครื่องและสิทธิ์ |
| 6 | ระบบปลายทางของ SFTP Feed คือระบบใด ใครดูแล | กำหนดผู้ประสานงานและ SLA ของ Feed |
| 7 | ใครคือผู้อนุมัติการเปลี่ยนแปลงระบบ | ตั้งขั้นตอน change management |
| 8 | ใครดูแลระบบหลัง go-live และช่วงเวลาใด | กำหนดรูปแบบการสนับสนุน |
| 9 | งบประมาณ/กรอบเวลาสำหรับ Phase 4 | เลือกระหว่างยกระดับกับพัฒนาใหม่ |
| 10 | มีข้อกำหนดจากผู้กำกับ/ผู้ตรวจสอบที่ต้องปฏิบัติเพิ่มหรือไม่ | ปรับแผนให้สอดคล้อง |

## 8. ข้อเสนอแนะสรุป

1. **แยกสองเรื่องออกจากกันให้ชัด** — (ก) ทำให้ระบบ Production ปัจจุบันมั่นคงและปลอดภัย
   (เร่งด่วน) กับ (ข) การพัฒนาระบบใหม่ในอนาคต — อย่ารวมเป็นแผนเดียวเพราะความเร่งด่วนต่างกัน
2. **เริ่มจากความปลอดภัยของบัญชีและรหัสผ่านทันที** — เป็นงานที่ใช้เวลาน้อย ต้นทุนต่ำ
   แต่ลดความเสี่ยงได้มากที่สุด
3. **ต้องได้ตัวเลข RTO/RPO จากเจ้าของระบบก่อน** จึงจะออกแบบการสำรอง/DR ได้อย่างมีเหตุผล
4. **ยอมรับตามตรงว่ารันไทม์เดิมหมดการสนับสนุน** และเสนอเป็นแผนระยะกลาง ไม่ควรปล่อยไว้เฉย ๆ
5. **ต่อยอดของดีที่มีอยู่** — งาน SFTP Feed ทำมาตรฐานได้ดี (script ทำซ้ำได้ + ชุดทดสอบ)
   ให้ใช้เป็นต้นแบบกับงานอื่น
